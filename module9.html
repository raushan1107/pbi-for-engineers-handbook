Publishing, Collaboration & Security

A Power BI report that only lives on your laptop delivers zero value. This module takes RR_EngineerWorks_v8.pbix from your desktop to the cloud — publishing to the Power BI Service, assigning row-level security to real users, scheduling automatic data refresh, and distributing the report across your organisation.

Publishing to Power BI Service

What "Publish" Does

Publishing uploads a .pbix file to a workspace in the Power BI Service (app.powerbi.com). It creates two separate artefacts in that workspace:

ArtefactWhat it containsWho uses it
Semantic model (dataset) Tables, relationships, measures, RLS role definitions, and any imported data Report builders; other reports can connect to the same model
Report All report pages, visuals, formatting, and bookmark state End users and stakeholders who interact with the data

The two artefacts are independent once published. You can build additional reports from the same semantic model, and you can refresh the model's data without touching the report layout.

How to Publish from Desktop
  1. In Power BI Desktop, click Home → Publish (or press Shift+F5).
  2. Sign in with your Microsoft 365 / Power BI account if prompted.
  3. In the Publish to Power BI dialog, select a destination workspace. Use a shared workspace for anything others need to access — My workspace is visible only to you.
  4. Click Select. The upload progress bar appears.
  5. When the success dialog appears, click the link to open the report directly in the browser.

Re-publishing to the same workspace replaces the existing dataset and report — it does not create duplicates. Any configurations set in the Service (scheduled refresh, RLS user assignments) survive an overwrite and do not need to be re-configured.

Workspaces & Permissions

What Is a Workspace?

A workspace is a container in the Power BI Service for datasets, reports, dashboards, and dataflows owned by a team or project. Every user has a personal My workspace that only they see. Shared workspaces support team collaboration with role-based access.

Use shared workspaces for any dataset that needs to be maintained by more than one person, refreshed on a schedule, or consumed by a broader audience via an app.

Workspace Roles
RoleCan doCannot do
Admin Full control — publish, edit, delete, share, manage members, configure gateway Nothing — has all permissions
Member Publish, edit, share content; manage data sources; cannot manage workspace membership Add/remove workspace members, delete the workspace
Contributor Publish and edit content; cannot share or manage data sources Share reports, manage gateway connections, manage members
Viewer View and interact with reports; export if the report author permits Edit, publish, or share anything; subject to RLS enforcement

Workspace Admins, Members, and Contributors bypass RLS — they see all data regardless of any RLS role assignment. Only Viewers are subject to RLS. This is intentional: report builders need full data to design and test.

Creating a Shared Workspace
  1. In the left nav, click Workspaces → Create a workspace.
  2. Enter a name (e.g. RR EngineerWorks Analytics) and an optional description.
  3. Expand Advanced → License mode — select Pro, PPU, or Fabric depending on your licence.
  4. Click Apply. The workspace is created and you are its Admin.
  5. Click Manage access to add team members and assign their roles.
Workspace Access vs Direct Report Sharing

There are two distinct ways to give someone access to a report:

  • Workspace membership: The person is added to the workspace with a role. They see all content in that workspace. Use for colleagues who build or maintain reports.
  • Direct report sharing: A specific report link is shared with an individual or group. They see only that report, not other workspace content. Use for stakeholders who only consume results.

For broad distribution to many users, build a workspace app (covered in Topic 5). An app gives users a curated, branded portal without exposing the underlying workspace content list or dataset settings.

Scheduled Refresh & Gateway

Why Refresh Is Needed

In Import mode, data is copied into the Power BI dataset at publish time. The cloud dataset does not auto-sync with the source — it is a static snapshot until you refresh it. A scheduled refresh runs automatically on a timetable so stakeholders always see current data.

Without scheduled refresh, anyone viewing the Service report sees data frozen at the moment you last clicked Publish.

DirectQuery and Live Connection modes query the source live on demand — they do not need scheduled refresh. However, they require the gateway service to be running continuously, and query performance depends on the source system.

On-Premises Data Gateway

If your data source is on a local network (SQL Server, file share, SAP, Analysis Services), the on-premises data gateway acts as a secure bridge between the Power BI Service in the cloud and your internal network. It is installed as a Windows service on a machine that can reach both the internet and the data source.

Gateway modeUse caseSuitable for
Standard (recommended)Shared across multiple datasets and users; administered centrallyProduction use — multiple people, multiple datasets
Personal modeSingle-user, simple local setupDevelopment and testing only; not suitable for shared workspaces

For cloud sources (SharePoint Online, Azure SQL, Dataverse, Excel in OneDrive), no gateway is required — the Service connects directly.

Configuring Scheduled Refresh

In the workspace, find the semantic model → three-dot menu → Settings → Scheduled refresh:

  1. Toggle Keep your data up to date to On.
  2. Set Refresh frequency: Daily or Weekly.
  3. Add time slots — when the refresh should run. Pick times when the source system is accessible and user traffic is low.
  4. Set the time zone to match your data's local time.
  5. Enter a failure notification email — you want to know immediately if a refresh fails.
  6. Click Apply.
Refresh History & Common Failures

In dataset settings → Refresh history: a log of every refresh attempt with status (Success / Failed) and duration. Expand a failed row for the error message. Common causes:

ErrorCauseFix
Gateway offlineGateway service stopped or server unreachableRestart the gateway Windows service; check firewall rules
Credentials expiredSource password changed since last configurationUpdate in Settings → Data source credentials
Schema changedColumn renamed or removed at the sourceFix in Power Query → republish
Timeout (2 h default)Dataset too large for one refresh windowIncremental refresh (Premium/Fabric); archive old data

Row-Level Security in the Service

The Two-Step RLS Process

RLS in Power BI has a clear division between Desktop and Service:

StepToolWhat you do
1 — Define rolesPower BI DesktopCreate role names + DAX filter expressions (done in Lab 8F)
2 — Assign membersPower BI ServiceMap users or security groups to the roles defined in Desktop

Neither step alone enforces security. A role with no members assigned is never applied. A user with no role assignment sees all data — the same as an admin view.

Assigning Users to RLS Roles
  1. In the workspace, find the semantic model (not the report) → three-dot menu → Security.
  2. The Row-level security pane shows all roles defined in the Desktop file.
  3. Click a role name (e.g. North England Manager) → type a user email or a Microsoft Entra security group in the Members box → press Enter.
  4. Click Save. The assignment is effective immediately — no re-publish needed.

Prefer security groups over individual emails. When Sarah joins or leaves the North England team, IT updates her group membership in Entra — no Power BI admin action needed.

Testing RLS in the Service

On the Row-Level Security page, click Test as role next to any role. The report opens restricted to that role's filter — the equivalent of "View as" in Desktop. A banner at the top identifies the active role. Click Stop viewing to return to the full admin view.

Always test each RLS role before notifying users. A misconfigured DAX filter can expose more data than intended or accidentally block all data.

Dynamic RLS — USERPRINCIPALNAME()

The static role from Module 8 hard-codes "North England". One role per region means 10 roles to create and maintain. The scalable pattern uses USERPRINCIPALNAME(), which returns the email of the currently-signed-in user: 

-- Dim_Regions table filter for a role named "Regional Manager"
[RegionName] IN
CALCULATETABLE(
    VALUES(UserRegionMap[RegionName]),
    UserRegionMap[UserEmail] = USERPRINCIPALNAME()
)

UserRegionMap is a two-column lookup table (UserEmail, RegionName) loaded into the model. If Sarah is mapped to both "North England" and "Midlands", she sees both. Changing her access requires only editing the lookup table row — no new roles, no republishing.

Publishing a Workspace App

A workspace app provides a branded, curated portal — the recommended way to distribute reports to a large audience without giving them workspace access.

  1. In the workspace, click Create app (top right).
  2. Setup tab: Name, description, logo, and optional support URL.
  3. Content tab: Select which reports and dashboards to include. Organise into named sections if needed (e.g. "Sales", "Operations").
  4. Audience tab: Specific users/groups or the entire organisation. Audience members can be different from workspace members.
  5. Click Publish app. App users find it under Apps in the left nav.

When you update a report and republish to the workspace, click Update app to push the new version to all app users — no action needed on their end.

Email Subscriptions

Open the report → Subscribe icon (envelope, top menu). Configure recipients, schedule (daily/weekly/specific days and times), subject line, and whether to include a report link. The snapshot respects the report's default slicer state but not individual user filters.

For personalised subscriptions where each recipient sees only their RLS-filtered data, use per-recipient subscriptions — a Premium/Fabric feature.

Copilot & Microsoft Fabric

What Is Microsoft Fabric?

Microsoft Fabric is a unified analytics platform that combines data engineering, data science, data warehousing, real-time intelligence, and business intelligence in a single SaaS product. Power BI is the visualisation and reporting layer within Fabric — the part this handbook has focused on.

The key architectural concept is OneLake: a single logical data lake shared across all Fabric workloads. Data ingested by a pipeline lands in OneLake. A Lakehouse or Warehouse sits on top. Power BI reports query it directly — eliminating the copies-of-copies problem common in traditional data architectures.

Fabric workloadWhat it doesAnalogy in this course
Data FactoryETL/ELT pipelinesPower Query at enterprise scale
LakehouseDelta-format data lake with SQL and Spark accessYour .pbix dataset, but open and shareable
WarehouseFull T-SQL data warehouse on OneLakeDirectQuery to a SQL Server
NotebooksPython/Spark notebooks for data science and MLPython visuals, but with data engineering power
Real-Time IntelligenceStreaming ingestion and KQL queriesReal-time dashboards beyond scheduled refresh
Power BIReports and dashboardsEverything in this handbook
Copilot in Power BI

Copilot is an AI assistant embedded in Power BI Desktop and the Service that uses large language models to accelerate report creation and analysis. Current capabilities (as of 2025):

  • Generate report pages: Describe what you need in plain text — Copilot places visuals, selects measures, and builds the page layout.
  • Summarise insights: Adds a Smart Narrative-style text visual with auto-generated observations about the page's data.
  • Answer questions: In the Copilot pane, ask "Which region had the highest revenue in Q3?" — Copilot queries the model and returns a direct answer or chart.
  • Write DAX: In Desktop with Copilot enabled, describe a measure in English — Copilot generates the DAX code for review.

Copilot requires a Fabric capacity (F64 or above) or PPU licence and must be enabled by your tenant admin. Output quality depends heavily on clear measure names, table descriptions, and semantic model hygiene — the work done in Modules 4 and 5 pays off directly here.

When to Move to Fabric
  • Your dataset exceeds the Power BI Pro 1 GB limit.
  • Multiple teams need to collaborate on pipelines, transformations, and reports in a governed platform.
  • Real-time or near-real-time analytics are needed beyond what scheduled refresh supports.
  • Data scientists need Python/Spark notebooks sharing the same data as Power BI reports.
  • The organisation wants a unified data estate with OneLake rather than siloed data copies.

For most engineering teams starting their Power BI journey, Pro workspaces are the right starting point. Fabric becomes the natural next step when report volumes, data volumes, and collaboration complexity grow.

Lab 9A — Publish to the Power BI Service
1
Publish from Desktop

Open RR_EngineerWorks_v8.pbix in Power BI Desktop. Click Home → Publish. Sign in if prompted.

Lab 9B — Create a Shared Workspace and Configure Access
1
Create a shared workspace

In the Service left nav, click Workspaces → Create a workspace. Name it RR EngineerWorks Analytics. Add a description such as "Sales, production, and regional performance analytics for RR EngineerWorks." Under Advanced → License mode, select Pro (or the highest available on your account). 2
Re-publish to the shared workspace

Return to Power BI Desktop. Click Home → Publish → select RR EngineerWorks Analytics → Select. If prompted to replace the existing content, click Replace.

3
Add a team member

In the workspace, click Manage access (top right). Add at least one other person (a colleague or a second test account) with the Viewer role. Click Add.

Viewer is the correct role for stakeholders who only need to read reports — not publish, edit, or share.

✓ Lab 9B Checkpoint

Lab 9C — Assign Users to RLS Roles
1
Open the dataset security settings

In the workspace, find the RR_EngineerWorks_v8 item with type Semantic model. Click its three-dot menu → Security.

Assign a user to the role

Click North England Manager. In the Members text box, type an email address (your own or a test account) → press Enter. Click Save.

Lab 9D — Configure Scheduled Refresh
1
Open dataset settings

In the workspace, click the RR_EngineerWorks_v8 semantic model three-dot menu → Settings. Expand the Scheduled refresh section.

This dataset was published from a local Excel file. The Service cannot reach a file on your local machine without a Personal Gateway installed. The configuration steps below will work — but the refresh itself will fail unless a gateway is set up. That is expected. The goal is to learn the configuration workflow.

2
Set the refresh schedule

Toggle Keep your data up to date to On. Configure:

  • Refresh frequency: Daily
  • Time zone: your local time zone
  • Time: add a slot at 06:00 (before the working day)
  • Send refresh failure notifications to: your email address

Click Apply.

✓ Lab 9D Checkpoint

  • Settings applied (Apply button clicked).
