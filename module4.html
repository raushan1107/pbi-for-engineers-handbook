Data Modelling & Semantic Design

Clean data is necessary but not sufficient. A well-designed semantic model is what turns seven separate tables into a coherent analytical system — one where every measure filters correctly, every visual drills intuitively, and every report developer shares the same definitions. This module builds the star schema that every DAX expression in Modules 5 and 6 will depend on.

What Is a Semantic Model?

Definition

A semantic model (also called a data model or dataset in Power BI Service) is a layer that sits between your raw tables and your report visuals. It defines how tables relate to each other, which calculations are official, and what the data means in business terms — not just what it is in technical terms.

Without a semantic model, every report developer writes their own SUM or AVERAGE and interprets "sales" differently. With one, everyone queries the same Total Sales measure and gets the same number from the same definition.

What a Semantic Model Contains
ComponentWhat it does
TablesThe cleaned, typed data from Power Query (our seven tables after Module 3)
RelationshipsLinks between tables — defines how filters flow from one table to another
MeasuresNamed DAX calculations (Total Sales, Variance %, etc.) shared across all reports
HierarchiesDrill paths for visuals (Year → Quarter → Month → Date; Category → SubCategory → Product)
Visibility rulesWhich columns are hidden from report view (FK columns, raw keys), which are exposed
DescriptionsHuman-readable labels on columns and measures that appear in tooltips
Why Engineers Should Care

Engineers are accustomed to defining system interfaces carefully — the contract between a sensor and a data pipeline, or between a module and its API, is explicit and versioned. A semantic model serves the same role for analytics: it is the published contract between your data and the people who build reports on it. Changes to the model are deliberate, documented, and reviewed — not ad hoc.

Fact & Dimension Tables

Fact Tables

A fact table records events — transactions, measurements, or observations. Each row is one event. Fact tables are typically wide (many columns), tall (many rows), and contain numeric measures you want to aggregate plus foreign keys that link to dimension tables.

In our model we have three fact tables:

TableRowsWhat each row representsKey numeric measures
Fact_Orders 585 One sales order line Quantity, UnitPrice, DiscountPct, TotalAmount
Fact_Production 288 One month's production run at one plant for one product PlannedUnits, ActualUnits, DefectRate_Pct, ShiftCount
Fact_Targets 120 One region's sales target for one month Target
Dimension Tables

A dimension table describes who, what, where, and when. Each row is a unique entity (a product, a customer, a date). Dimensions are narrow (fewer columns) and short (fewer rows). They hold the descriptive attributes that give your aggregations context — "sales by region", "defects by product category", "orders per customer segment".

TableRowsWhat each row representsKey descriptors
Dim_Products 30 One unique product ProductName, Category, SubCategory, UnitCost, ListPrice, Status
Dim_Customers 80 One unique customer account CompanyName, ContactName, City, Country, Segment
Dim_Regions 10 One geographic region RegionName, Territory, Country, RegionalManager
Dim_Date 5 (scaffold) One calendar date Year, Quarter, Month, MonthName, Day, IsWeekend, FiscalYear

Note: Dim_Date currently holds only 5 scaffold rows. You will replace it with a full 366-row calendar (2024 is a leap year) using DAX's CALENDARAUTO function in Module 6. The relationship you build in this module will carry over automatically.

One Table That's Neither

HR_Directory was loaded in Module 2 and its load was disabled in Module 3. It has no matching key in any other table (EmployeeID appears only in HR_Directory) and is therefore disconnected. It does not participate in the model and does not appear in Data view or Field list.

3

Star vs Snowflake Schema

The Star Schema

In a star schema, each fact table sits at the centre and connects directly to denormalized dimension tables. The result looks like a star — one hub, many spokes. All filtering happens through a single join hop between a dimension and a fact.

Star schemas are the standard for Power BI and other columnar analytical engines because they are fast (fewer joins), simple to query (one hop from any dimension to any fact), and unambiguous (no multi-path filter propagation).

The Snowflake Schema (and When to Avoid It)

In a snowflake schema, dimension tables are normalized — a product dimension might reference a separate category dimension, which references a separate department dimension. This saves storage in row-based OLTP systems but hurts performance in columnar analytical engines.

In Power BI: flatten snowflake dimensions before loading. If your source has a separate Category table, merge it into Dim_Products in Power Query so that Dim_Products contains all product attributes in one table. This is exactly why Module 3 split Category_SubCategory into two separate columns within Dim_Products rather than creating a separate Category table.

Our Model: Two Fact Tables Share Dimensions

The RR EngineerWorks model has three fact tables that share the same dimension tables. This pattern — sometimes called a conformed dimension — means that "Total Sales by Region" and "Production Units by Region" both filter through the same Dim_Regions table. Cross-filtering works consistently, and you can create visuals that show both fact tables side-by-side on the same region dimension. 

Dim_Products ←──── Fact_Orders ────→ Dim_Customers
                       │
                 Dim_Regions ←────┘ (also via RegionID)
                       │
                 Dim_Date   ←────┘ (via OrderDate)

             Fact_Production ──→ Dim_Products (shared)
             Fact_Targets    ──→ Dim_Regions  (via RegionName — text join)
             Fact_Targets    ──→ Dim_Date     (via MonthStart)

Relationships & Cardinality

Cardinality

Cardinality describes how many rows on one side of a relationship match rows on the other side.

CardinalityMeaningExample
Many-to-One (*:1) Many rows in the fact table can reference one row in the dimension Many orders → one customer
One-to-One (1:1) Each row on both sides is unique Rare in analytical models; often indicates tables should be merged
Many-to-Many (*:*) Duplicate keys on both sides Usually a data quality problem — fix the data first

All seven relationships in our model will be Many-to-One — the fact table is on the many side, the dimension is on the one side. Power BI detects cardinality automatically when you create a relationship; if it shows Many-to-Many, that is a signal that the join column has duplicates in the dimension table (a data quality issue to investigate).

Cross-Filter Direction

Cross-filter direction controls how filters flow across a relationship when a visual or measure applies a filter.

DirectionBehaviourRecommendation
Single Filters flow from the dimension (one side) to the fact (many side) only Default — use this for all relationships
Both (Bidirectional) Filters flow in both directions — a fact filter can slice a dimension Avoid unless required. Causes ambiguous filter paths and performance issues. Implement with CROSSFILTER() in DAX instead.
Active vs Inactive Relationships

Power BI allows only one active relationship between any two tables. Active relationships are shown as solid lines in Model view; inactive relationships are dashed. Only active relationships participate automatically in filtering.

We have two relationships from fact tables to Dim_Date (from Fact_Orders and from Fact_Targets) and two relationships to Dim_Products (from Fact_Orders and from Fact_Production). These are between different fact tables, so there is no conflict — each pair of tables has at most one relationship.

The Text-Join Relationship (Fact_Targets → Dim_Regions)

Most relationships in our model join on integer or code columns (RegionID, ProductCode, CustomerID). The Fact_Targets to Dim_Regions relationship is different — it joins on RegionName (text). This is why Module 3 Lab 3F replaced "Europe - International" with "Europe" in Fact_Targets — without that fix, the join column wouldn't match Dim_Regions and the relationship would leave one region's targets unmatched.

Text-join relationships are slightly slower than integer joins in large models, but for 120-row Fact_Targets it makes no practical difference. The alternative would be to add a RegionID column to Fact_Targets, but that would require adding a lookup to the source data — more complex than a simple replace.

5

Creating a Date Table

Why a Date Table is Mandatory

DAX's time intelligence functions (TOTALYTD, DATESINPERIOD, SAMEPERIODLASTYEAR, etc.) only work if your model has a proper Date table — a table where:

  • Every date in the range has exactly one row (no gaps)
  • The date range covers all dates in any fact table's date column
  • The table is explicitly marked as a Date table in Power BI

Without a marked Date table, Power BI cannot correctly calculate year-to-date totals, prior-period comparisons, or rolling windows — even if you have a date column in your fact table.

Our Approach: CALENDARAUTO in Module 6

The dataset includes a Dim_Date sheet with 5 scaffold rows showing the expected schema. In Module 6, you will replace those rows with a full calendar using DAX's CALENDARAUTO() function — which automatically spans all dates referenced across all loaded fact tables.

For RR EngineerWorks, OrderDate ranges from 1 Jan 2024 to 31 Dec 2024, and MonthStart in Fact_Targets covers the same year. CALENDARAUTO will generate all 366 dates (2024 is a leap year). The relationship you create in this module will work immediately with the scaffold and will carry over unchanged when you replace the table in Module 6.

Model Optimization

Hide, Don't Delete

Foreign key columns (RegionID in Fact_Orders, ProductCode in Fact_Orders, etc.) are needed for the relationship to function but should not appear in report visuals — users should filter by Dim_Regions[RegionName], not by Fact_Orders[RegionID]. Right-click a column → Hide in report view to remove it from the Fields pane without deleting it from the model.

Hidden columns still participate in relationships and can be used in DAX expressions. They just don't clutter the Fields pane for report developers.

The _Measures Table

By default, measures are stored in the table where they were created. After a few dozen measures, the Fields pane becomes hard to navigate. The convention is to create a dedicated empty table named _Measures and store all measures there. The underscore prefix sorts it to the top of the Fields pane.

The table is created via Home → Enter Data: give it the name _Measures, leave the data grid empty (one blank row is fine), and click Load. The table appears in the model with no columns exposed — just a container for your measures.

Building Hierarchies

What Hierarchies Do

A hierarchy defines a drill-down path for visuals. When a hierarchy is attached to a visual's axis, the user can click a data point to "drill into" the next level. Without an explicit hierarchy, Power BI requires the user to manually swap out the axis field.

Hierarchies live in dimension tables. They do not change the underlying data — they are metadata that Power BI uses to expose the drill path in the visual UX.

Two Hierarchies for Our Model
HierarchyTableLevels (top → bottom)
Product Hierarchy Dim_Products Category → SubCategory → ProductName
Date Hierarchy Dim_Date Year → Quarter → Month → Date

The Date Hierarchy is created on Dim_Date's existing columns (Year, Quarter, Month, Date). Even with only 5 scaffold rows now, the hierarchy structure is valid. When Module 6 replaces Dim_Date with 366 rows, the hierarchy works immediately.

How to Create a Hierarchy

In Model view or Data view, right-click the top-level column → Create hierarchy. Power BI creates a hierarchy node named Column Name Hierarchy. Rename it. Then drag subsequent columns onto the hierarchy node to add levels — or right-click each column → Add to hierarchy.

You will build the complete star schema for RR EngineerWorks: seven relationships, a measures table, two hierarchies, and a set of hidden FK columns. Every instruction in this lab has been verified against the actual dataset columns from Module 3.

Lab 4A — Build the Star Schema (7 Relationships)
1
Open your Module 3 file and navigate to Model view

Open RR_EngineerWorks_v3.pbix. On the left sidebar of Power BI Desktop, click the Model view icon (the three connected boxes). You should see all seven loaded tables arranged as a cloud of separate boxes: Fact_Orders, Dim_Products, Dim_Customers, Dim_Regions, Dim_Date, Fact_Production, and Fact_Targets. They will not be connected yet.

HR_Directory does not appear because its load is disabled (Module 3 Lab 3G).

2
Relationship 1 — Fact_Orders → Dim_Products

Drag Fact_Orders[ProductCode] onto Dim_Products[ProductCode]. The Manage Relationship dialog opens. Confirm:

  • Cardinality: Many to One (*:1) — Fact_Orders is Many, Dim_Products is One
  • Cross filter direction: Single
  • Active: checked

Click OK. A solid line now connects the two tables.

3
Relationship 2 — Fact_Orders → Dim_Customers

Drag Fact_Orders[CustomerID] onto Dim_Customers[CustomerID]. Confirm cardinality Many-to-One, direction Single, Active checked. Click OK.

✓ Checkpoint
  • Cardinality shows Many-to-One. If it shows Many-to-Many, CustomerID still has non-C{NNN} values — go back to Module 3 Lab 3B Fix 3 and re-run Close & Apply.
4
Relationship 3 — Fact_Orders → Dim_Regions

Drag Fact_Orders[RegionID] onto Dim_Regions[RegionID]. Confirm Many-to-One, Single, Active. Click OK.

Note: Fact_Orders has ~5% null RegionIDs (28 rows) — these orders had no region recorded in the source data. They appear in Fact_Orders but will not match any row in Dim_Regions. Power BI handles this correctly by treating them as "blank" in any region-sliced visual — not as an error.

5
Relationship 4 — Fact_Orders → Dim_Date

Drag Fact_Orders[OrderDate] onto Dim_Date[Date]. Confirm Many-to-One, Single, Active. Click OK.

If you see a type mismatch warning: the Dim_Date scaffold may have loaded the Date column as Text (the Excel cells are formatted DD/MM/YYYY). Open Power Query: select the Dim_Date query → click the ABC icon on the Date column header → Date → in the locale prompt choose English (United Kingdom) → OK → Close & Apply. Then create the relationship.

6
Relationship 5 — Fact_Production → Dim_Products

Drag Fact_Production[ProductCode] onto Dim_Products[ProductCode]. Confirm Many-to-One, Single, Active. Click OK.

Dim_Products now connects to two fact tables: Fact_Orders and Fact_Production. This is a conformed dimension — the same product catalogue drives both sales and production analysis.

7
Relationship 6 — Fact_Targets → Dim_Regions (text join)

Drag Fact_Targets[RegionName] onto Dim_Regions[RegionName]. Confirm Many-to-One, Single, Active. Click OK.

This is a text-to-text join, not an ID join. It works because Module 3 Lab 3F replaced "Europe - International" with "Europe" in Fact_Targets — so all 10 RegionName values in Fact_Targets now exactly match the 10 RegionName values in Dim_Regions.

✓ Checkpoint
  • Cardinality shows Many-to-One. If it shows Many-to-Many, Fact_Targets[RegionName] has values not in Dim_Regions[RegionName]. Open Power Query → Fact_Targets → check Column Distribution on RegionName for any value other than the 10 expected region names.
8
Relationship 7 — Fact_Targets → Dim_Date

Drag Fact_Targets[MonthStart] onto Dim_Date[Date]. Confirm Many-to-One, Single, Active. Click OK.

All 7 relationships are now in place. In Model view, your diagram should show a clear star pattern: three fact tables at the centre, each connected to the shared dimensions.

Lab 4C — Build Hierarchies
1
Create the Product Hierarchy in Dim_Products

In the Fields pane (or in Model view), expand Dim_Products. Right-click Category → Create hierarchy. A new node appears named Category Hierarchy.

Rename it: right-click the new hierarchy node → Rename → type Product Hierarchy → Enter.

Now add the next two levels:

  • Right-click SubCategory → Add to hierarchy → Product Hierarchy
  • Right-click ProductName → Add to hierarchy → Product Hierarchy

The hierarchy now shows three levels: Category → SubCategory → ProductName.

2
Create the Date Hierarchy in Dim_Date

Expand Dim_Date in the Fields pane. Right-click Year → Create hierarchy. Rename it to Date Hierarchy.

Add the next three levels:

  • Right-click Quarter → Add to hierarchy → Date Hierarchy
  • Right-click MonthName → Add to hierarchy → Date Hierarchy
  • Right-click Date → Add to hierarchy → Date Hierarchy

MonthName vs Month: We use MonthName ("January", "February") in the hierarchy for display labels. The Month column (integer 1–12) is useful for sorting — right-click MonthName → Sort by column → Month. This ensures months sort correctly instead of alphabetically. Set this sort-by on Dim_Date now, before building visuals in Module 7.

Lab 4D — Optimize the Model (Hide FK Columns)
1
Hide foreign key columns from Fact_Orders

In the Fields pane, right-click each of the following columns and choose Hide in report view:

  • Fact_Orders[ProductCode] — FK to Dim_Products
  • Fact_Orders[CustomerID] — FK to Dim_Customers
  • Fact_Orders[RegionID] — FK to Dim_Regions
  • Fact_Orders[OrderDate] — FK to Dim_Date (users filter through Dim_Date's Date Hierarchy)

Hidden columns show with a grey eye icon in Model view and disappear from the Fields pane in Report view.

2
Hide foreign key columns from Fact_Production and Fact_Targets

Right-click and hide:

  • Fact_Production[ProductCode] — FK to Dim_Products
  • Fact_Production[ProductionMonth] — date FK to Dim_Date
  • Fact_Targets[RegionName] — text FK to Dim_Regions
  • Fact_Targets[MonthStart] — date FK to Dim_Date
3
Hide technical columns from Dim_Date and Dim_Customers

These columns exist in the model but are not useful for report authors:

  • Dim_Date[DateKey] — integer surrogate key, not needed in visuals
  • Dim_Customers[RegionID] — the customer's home region. We analyse orders by region via Fact_Orders[RegionID], not by customer home region. Hiding prevents confusion.
  • Dim_Products[UnitCost] — not exposed to report authors (internal cost data). Leave ListPrice visible.
4
Set Sort by Column for MonthName

In the Fields pane, click Dim_Date[MonthName] to select it (it will appear highlighted in the Column Tools ribbon). In the Column Tools ribbon that appears at the top, find Sort by Column and select Month from the dropdown. This ensures that when MonthName is used in a visual, months sort January → December rather than alphabetically.
