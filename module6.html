Module 6

Advanced DAX & Time Intelligence

Two foundational concepts unlock advanced analytical power in Power BI. First, iterator functions let you compute row-by-row expressions and aggregate the results — essential when a simple SUM or AVERAGE is not enough. Second, time intelligence functions let you compare periods, calculate running totals, and analyse trends — but only with a properly built date table. This module builds both.

Row Context & Iterator Functions

Row Context

Row context is active when DAX is evaluating an expression one row at a time inside a table. It exists in two places:

  • Calculated columns: Each row of the column is computed in a row context — the formula can reference other columns in the same row directly (e.g. Fact_Orders[Quantity] * Fact_Orders[UnitPrice]).
  • Iterator functions: Functions like SUMX, AVERAGEX, RANKX iterate over every row of a table, evaluate an expression in the context of each row, and then aggregate the results.

Row context does not automatically propagate filters through relationships. A row context on Fact_Orders does not filter Dim_Products — you need RELATED() or RELATEDTABLE() to cross a relationship inside row context.

SUMX — The Most Important Iterator

SUMX(table, expression) iterates over every row of table, evaluates expression in the row context of each row, and sums the results. It is the row-by-row equivalent of SUM. 

-- Gross revenue BEFORE discounts: Quantity × ListPrice per order row, then sum
Gross Revenue =
SUMX(
    Fact_Orders,
    Fact_Orders[Quantity] * Fact_Orders[UnitPrice]
)

-- This CANNOT be written as SUM(Fact_Orders[Quantity]) * SUM(Fact_Orders[UnitPrice])
-- because that multiplies totals, not row-level values

The key insight: SUM(col) sums a single column. SUMX evaluates an arbitrary expression per row first, then sums — enabling you to multiply, concatenate, or call functions at the row level before aggregating.

Table Functions

Functions That Return Tables

DAX has a family of functions that return entire tables. These tables can be used as the first argument to iterator functions, as filter arguments in CALCULATE, or to create calculated tables.

FunctionReturnsCommon use
ALL(table_or_column)All rows of a table ignoring all filtersRemove a filter in CALCULATE for denominators
ALLEXCEPT(table, col1, col2)All rows except those filtered by the specified columnsKeep one dimension filter, remove others
FILTER(table, condition)Rows from table where condition is TRUEPass a filtered table to an iterator
VALUES(column)Distinct values in column under current filterIterate over distinct values; counts
DISTINCT(column)Distinct values ignoring blankSimilar to VALUES but excludes blank row
ADDCOLUMNS(table, name, expr, ...)Table with extra computed columns appendedBuilding calculated tables like the Date table
FILTER Inside CALCULATE

While a boolean filter like Fact_Orders[OrderStatus] = "Completed" is the preferred syntax for simple column filters, FILTER is needed when the filter involves a measure (not a column value): 

-- All regions where sales exceed £100,000 (measure-based filter — needs FILTER)
High Value Regions Sales =
CALCULATE(
    [Total Sales],
    FILTER(
        ALL(Dim_Regions),
        [Total Sales] > 100000
    )
)

Do not use FILTER for simple column-value filters — the boolean syntax is faster because Power BI can push it to the storage engine directly.

Date Table for Time Intelligence

Requirements for a Valid Date Table

Power BI requires a date table to meet three conditions before time intelligence functions will work:

  1. A contiguous date column with no gaps — every date from the start to the end of the range must have exactly one row
  2. The column must be typed as Date (not DateTime, not Text)
  3. The table must be marked as a Date table via the Table Tools ribbon

The 5-row scaffold in Dim_Date fails condition 1 — it has gaps. We replace it in the lab with a complete 366-row calendar (2024 is a leap year: 1 Jan 2024 to 31 Dec 2024 = 366 days).

Two Ways to Build a Full Date Table
ApproachWhereProsCons
M code in Power Query Power Query Advanced Editor on the Dim_Date query Replaces the scaffold directly; no duplicate table; refreshes from source Requires Power Query / M knowledge
CALENDARAUTO + ADDCOLUMNS DAX calculated table (Modeling tab → New Table) Pure DAX; CALENDARAUTO auto-detects date range from all fact tables Creates a second table; must delete or disable the old scaffold

In this lab we use the Power Query M code approach, which replaces the existing Dim_Date query in-place and preserves all relationships defined in Module 4.

CALENDARAUTO (Reference)

CALENDARAUTO() is a DAX function that generates a table with a single Date column containing every date from the earliest to the latest date referenced in all loaded fact tables. Combined with ADDCOLUMNS, it builds a complete date table: 

Dim_Date_Full =
ADDCOLUMNS(
    CALENDARAUTO(),
    "Year",        YEAR([Date]),
    "Quarter",     QUARTER([Date]),
    "QuarterName", "Q" & QUARTER([Date]),
    "Month",       MONTH([Date]),
    "MonthName",   FORMAT([Date], "MMMM"),
    "Day",         DAY([Date]),
    "DayOfWeek",   FORMAT([Date], "DDDD"),
    "IsWeekend",   IF(WEEKDAY([Date], 2) >= 6, 1, 0),
    "FiscalYear",  "FY" & YEAR([Date])
)

For RR EngineerWorks (all fact dates in 2024), CALENDARAUTO generates exactly 366 rows — 1 Jan 2024 through 31 Dec 2024.

Time Intelligence Functions

How They Work

Time intelligence functions modify the filter context on the date table to represent a different time period. They all accept the date column of the marked date table as their argument, and most return a set of dates (a table of dates) that CALCULATE then uses to filter the model.

Cumulative Totals
FunctionReturns dates fromExample measure
TOTALYTD(expr, dates) Start of year to end of current period TOTALYTD([Total Sales], Dim_Date[Date])
TOTALMTD(expr, dates) Start of month to end of current period TOTALMTD([Total Sales], Dim_Date[Date])
TOTALQTD(expr, dates) Start of quarter to end of current period TOTALQTD([Total Sales], Dim_Date[Date])
Period Comparison Functions
FunctionReturnsUse case
SAMEPERIODLASTYEAR(dates) Same period one year ago Year-on-year comparison
PREVIOUSMONTH(dates) The entire prior calendar month Month-over-month comparison
PREVIOUSQUARTER(dates) The entire prior calendar quarter Quarter-over-quarter comparison
DATESINPERIOD(dates, lastdate, n, interval) A rolling window of n intervals back from lastdate Rolling 3-month, 12-month windows
Usage Pattern

All period-comparison functions are used inside CALCULATE: 

Total Sales LY =
CALCULATE(
    [Total Sales],
    SAMEPERIODLASTYEAR(Dim_Date[Date])
)

Rolling 3M Sales =
CALCULATE(
    [Total Sales],
    DATESINPERIOD(
        Dim_Date[Date],
        LASTDATE(Dim_Date[Date]),
        -3,
        MONTH
    )
)

Year-on-Year Growth

The YoY Pattern

Year-on-year (YoY) growth compares the current period to the same period in the prior year. The standard three-measure pattern is: 

-- Step 1: Current period measure (already exists as [Total Sales])

-- Step 2: Prior year equivalent
Total Sales LY =
CALCULATE([Total Sales], SAMEPERIODLASTYEAR(Dim_Date[Date]))

-- Step 3a: Absolute growth
YoY Sales Growth = [Total Sales] - [Total Sales LY]

-- Step 3b: Percentage growth (safe divide in case LY is BLANK)
YoY Sales Growth % = DIVIDE([YoY Sales Growth], [Total Sales LY])
Single-Year Dataset Note

The RR EngineerWorks dataset covers only 2024. SAMEPERIODLASTYEAR will look at 2023, which has no data — so [Total Sales LY] will return BLANK() for all dates. The YoY measures exist in the model as a structural pattern: they will produce real results the moment multi-year data is loaded. Power BI visuals hide BLANK values cleanly — no errors appear.

To verify the pattern works correctly, you can temporarily hard-code a prior year total using CALCULATE([Total Sales], Dim_Date[Year] = 2023) (also returns BLANK for this dataset) and confirm the ratio formula handles it without errors.

Semi-Additive Measures

Additive vs Semi-Additive vs Non-Additive

Most financial and transactional measures are fully additive: Total Sales for Q1 = Jan Sales + Feb Sales + Mar Sales. You can SUM across any dimension and time period and get a meaningful result.

Semi-additive measures add correctly across some dimensions but not across time. A stock level or headcount at month-end is meaningful per month, but summing January's stock + February's stock gives a meaningless number — the correct aggregation over time is the last value or the average.

Non-additive measures (ratios, percentages, ranks) cannot be summed at all — Production Efficiency % for Jan + Feb ≠ Efficiency for the combined period. Always recompute from numerator + denominator.

LASTNONBLANK for Semi-Additive Measures

For "last known value" semi-additive measures, use LASTNONBLANK(dates, expression) to find the latest date that has a non-blank result: 

-- Example: last recorded ActualUnits (if tracking a running inventory)
Last Month Actual Units =
CALCULATE(
    SUM(Fact_Production[ActualUnits]),
    LASTNONBLANK(Dim_Date[Date], SUM(Fact_Production[ActualUnits]))
)

Our dataset does not have a balance-type measure (all measures are fully additive or non-additive ratios), so this is a reference pattern rather than a lab step.

7

Visual Calculations

What Visual Calculations Are

Visual calculations (introduced in Power BI Desktop in 2024) are DAX calculations defined directly on a visual — not in the model. They can reference the visual's "axis" (rows or columns) and neighbouring values in the visual matrix, which ordinary measures cannot do.

They enable patterns like:

  • Running totals within a visual without needing CALCULATE+FILTER DAX
  • Percent of total row / column in a matrix
  • Previous row value reference
  • Rank within the visual (vs RANKX which ranks across the full table)
How to Create a Visual Calculation

Select a matrix or table visual → in the ribbon, click Visual calculations (under the visual's formatting ribbon). A formula bar opens where you can write a DAX expression using special visual-context functions like RUNNINGSUM, PREVIOUS, INDEX, and WINDOW. 

-- Running total down the rows of the visual
Running Sales = RUNNINGSUM([Total Sales])

-- Percent of parent row total
Sales % of Total = DIVIDE([Total Sales], CALCULATE([Total Sales], ALLSELECTED()))
Visual Calculations vs Model Measures

Visual calculations are visual-only — they cannot be used in other visuals or reused across reports. Model measures (in _Measures) are reusable across all visuals and reports. Use visual calculations for ad hoc visual-specific layout calculations; use model measures for core business definitions.

This lab has three parts: rebuild Dim_Date as a full 366-row calendar, mark it as the date table, then add 8 new measures. Open RR_EngineerWorks_v5.pbix to begin.

Lab 6A — Rebuild Dim_Date (5 rows → 366 rows)
1
Open Power Query and select Dim_Date

Home → Transform Data to open Power Query Editor. In the Queries panel on the left, click Dim_Date. You will see the 5 scaffold rows from the Excel source.

2
Replace the query with a full date generation

On the Home tab, click Advanced Editor. Select all the existing M code and replace it entirely with: 

let
    StartDate  = #date(2024, 1, 1),
    EndDate    = #date(2024, 12, 31),
    TotalDays  = Duration.Days(EndDate - StartDate) + 1,
    DateList   = List.Dates(StartDate, TotalDays, #duration(1, 0, 0, 0)),
    DateTable  = Table.FromList(DateList, Splitter.SplitByNothing(),
                     type table [Date = date]),
    AddDateKey = Table.AddColumn(DateTable, "DateKey",
                     each Date.Year([Date]) * 10000
                       + Date.Month([Date]) * 100
                       + Date.Day([Date]),
                     Int64.Type),
    AddYear    = Table.AddColumn(AddDateKey, "Year",
                     each Date.Year([Date]), Int64.Type),
    AddQtr     = Table.AddColumn(AddYear, "Quarter",
                     each Date.QuarterOfYear([Date]), Int64.Type),
    AddQtrName = Table.AddColumn(AddQtr, "QuarterName",
                     each "Q" & Text.From(Date.QuarterOfYear([Date])),
                     type text),
    AddMonth   = Table.AddColumn(AddQtrName, "Month",
                     each Date.Month([Date]), Int64.Type),
    AddMthName = Table.AddColumn(AddMonth, "MonthName",
                     each Date.ToText([Date], "MMMM", "en-GB"),
                     type text),
    AddDay     = Table.AddColumn(AddMthName, "Day",
                     each Date.Day([Date]), Int64.Type),
    AddDow     = Table.AddColumn(AddDay, "DayOfWeek",
                     each Date.ToText([Date], "dddd", "en-GB"),
                     type text),
    AddWknd    = Table.AddColumn(AddDow, "IsWeekend",
                     each if Date.DayOfWeek([Date], Day.Monday) >= 5
                          then 1 else 0,
                     Int64.Type),
    AddFY      = Table.AddColumn(AddWknd, "FiscalYear",
                     each "FY" & Text.From(Date.Year([Date])),
                     type text),
    Reorder    = Table.ReorderColumns(AddFY, {
                     "DateKey","Date","Year","Quarter","QuarterName",
                     "Month","MonthName","Day","DayOfWeek","IsWeekend","FiscalYear"})
in
    Reorder

Click Done. Power Query now shows 366 rows in the Data preview (1 Jan 2024 to 31 Dec 2024). The column structure matches the original scaffold schema exactly.

Lab 6C — Iterator Functions (3 measures)
1
Measure 21 — Gross Revenue
Gross Revenue =
SUMX(
    Fact_Orders,
    Fact_Orders[Quantity] * Fact_Orders[UnitPrice]
)

Format: £#,0.00. This computes revenue before discounts — price × quantity per row, summed. It differs from [Total Sales] because TotalAmount already has discounts applied. You cannot compute this with a simple SUM because multiplying summed Quantity × summed UnitPrice gives an incorrect result when different rows have different prices.

2
Measure 22 — Total Discount Given
Total Discount Given = [Gross Revenue] - [Total Sales]

Format: £#,0.00. The difference between gross (pre-discount) revenue and net (post-discount) sales is the total discount value passed to customers.

3
Measure 23 — Region Sales Rank
Region Sales Rank =
RANKX(
    ALL(Dim_Regions),
    [Total Sales],
    ,
    DESC,
    DENSE
)

Format: #,0. In a table or matrix with Dim_Regions[RegionName] in rows, this measure shows each region's rank by Total Sales (1 = highest). ALL(Dim_Regions) ensures the rank is computed across all 10 regions regardless of any region slicer. DENSE means tied ranks share the same number without gaps (1, 1, 2, 3… instead of 1, 1, 3, 4…).

✓ Lab 6C Checkpoint

  • Region Sales Rank should show 1 through 10 with no gaps.
  • Apply a region slicer — the rank should remain 1–10 within all 10 regions (the ALL() in the measure ignores the slicer).
