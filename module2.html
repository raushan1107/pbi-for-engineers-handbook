Connectors Overview

Definition

A connector is a pre-built driver that teaches Power BI how to speak the language of a specific data source — its authentication protocol, its query dialect, its pagination behaviour. Power BI ships with over 150 built-in connectors, covering everything from a local Excel file to a live Salesforce org.

The Connector Families

Connectors fall into six broad families. Knowing which family your source belongs to tells you roughly what authentication you'll need and what refresh behaviour to expect.

FamilyCommon SourcesTypical AuthNotes
File-based Excel, CSV, XML, JSON, PDF, Folder None (local path) or Windows Simplest to start with. Folder connector lets you combine many files at once.
Relational DB SQL Server, PostgreSQL, MySQL, Oracle, Azure SQL Windows / SQL / OAuth Supports DirectQuery. Gateway needed for on-premises instances.
Microsoft 365 SharePoint, Teams, Dataverse, Dynamics 365 Microsoft account (OAuth) Lives in the cloud — no gateway needed for Service refresh.
Analytics / Cloud Azure Synapse, Databricks, Snowflake, BigQuery, Fabric OAuth / Service Principal Large-scale; often used in DirectQuery or composite mode.
Web / API Web (HTTP), OData Feed, REST APIs Anonymous / API Key / OAuth Flexible but can be fragile if the API schema changes.
Other SAP, IBM DB2, Salesforce, Google Analytics Varies Certified connectors from vendors; check gateway requirements.
Finding a Connector

Click Home → Get Data → More… to open the full connector gallery. The search box at the top filters instantly — type "share" to find SharePoint, "oracle" for Oracle, etc. If you can't find a connector for your source, check whether it's available as an OData or Web connector, or look for a custom connector from the vendor.

🔧 Analogy — Universal Power Adapter

Different countries use different plug shapes — UK three-pin, European two-pin, US flat-blade. A universal adapter translates between them so your single device can work anywhere. Power BI's connector library is that adapter kit. Each connector handles the plug-shape difference (API format, auth handshake, pagination) so that once data is inside Power BI it looks the same regardless of where it came from.

📊 RR EngineerWorks Sources

  • SQL Server (Fact_Production in a full enterprise setup — simulated via the Excel sheet in this handbook)
  • SharePoint List (Targets — simulated via the Targets_Wide sheet)
  • Web / OData (Currency exchange rates — optional extension in Module 8)
⭐ Key Takeaway

The connector is just the door. What matters is understanding which authentication type that door uses, whether you need a Gateway to open it from the Service, and which connectivity mode (Import / DirectQuery / Live) makes sense given your data volume and freshness requirements.

Combining Multiple Data Sources into One Model

Definition

Power BI allows you to connect to multiple sources in the same report. Each source becomes one or more queries in Power Query. After transformation, all tables land in the same semantic model where you build relationships between them — regardless of where the original data came from.

Why This Matters

Real business questions almost always span multiple systems. "Is the North England region hitting its sales target?" requires sales data from a CRM, target data from a finance spreadsheet, and region data from a master table — three separate sources. None of those individual systems can answer the question alone. Power BI's strength is pulling them together into one model where cross-source questions become trivial.

The important constraint: the tables must share a common key column so you can build a relationship. If the sales data uses RegionID but the target data uses free-text region names (like "Europe - International" in Targets_Wide vs "Europe" in Dim_Regions), you must fix that mismatch in Power Query before trying to draw a relationship. You'll do exactly this in Module 3.

Two Ways to Combine Data in Power Query
OperationWhat it doesWhen to use
Merge Queries JOIN — brings columns from a second table into the first based on a matching key column (like SQL JOIN). Enriching a fact table with lookup values. E.g. adding ProductName to Fact_Orders by matching on ProductCode.
Append Queries UNION — stacks rows from multiple tables on top of each other. All tables must have compatible column names. Combining monthly files from a folder, or unioning sales data from two regions into one table.

Note: In most star-schema designs you don't need Merge at the Power Query stage — you leave join logic to the Model (relationships). Merge is most useful when you need to carry a lookup value into a table for cleaning purposes, or when you want to denormalise deliberately.

🔧 Analogy — Investigative Journalist

An investigative journalist building a story gathers facts from newspaper archives, interview transcripts, public company filings, and leaked documents — each from a different source, each in a different format. The journalist's job is to synthesise them into one coherent narrative. Power BI's Power Query is the synthesis tool; the semantic model relationships are the editorial structure that makes the narrative hold together.

📊 RR EngineerWorks: 8 Sources → 1 Model

Your finished RR EngineerWorks model will load all 8 sheets from one Excel workbook, but in real enterprise use these would be separate systems:

  • Fact_Orders (from CRM / ERP export)
  • Fact_Production (from MES / SQL Server)
  • Dim_Products, Dim_Customers, Dim_Regions (from master data management system)
  • Targets_Wide (from Finance Excel/SharePoint)
  • HR_Directory (from HR system — you'll decide whether this table earns a place in the model at all)
  • Dim_Date (generated in Power BI itself, no external source)
⭐ Key Takeaway

Load each source as a separate query. Keep the join logic in Model relationships, not Power Query merges. Power Query merges are for cleaning; relationships are for analysis.

Import, DirectQuery, and Live Connection — When to Use Each

Definition

The connectivity mode determines where data lives and how queries are executed. This single decision affects report speed, data freshness, model size, and how much work your source database has to do.

Mode Where data lives Data freshness Query speed Volume limit
Import Copied into Power BI's in-memory engine (VertiPaq) inside the .pbix file As fresh as the last scheduled or manual refresh Fastest — queries run entirely in memory ~1 GB compressed (can reach billions of rows with efficient modelling)
DirectQuery Data stays in the source database; queries are sent live Real-time — always shows current database state Slower — depends on source DB performance and network Unlimited — queries the source directly
Live Connection Model is pre-built in Power BI Service, SSAS, or Azure AS; you add a report layer only Real-time to the existing model Fast (model is already optimised) Governed by the upstream model
The Decision Framework

Use this decision tree on every new project:

  1. Is the data over ~500M rows or growing unboundedly? → DirectQuery or composite mode.
  2. Does the business need data fresher than your refresh schedule? → DirectQuery.
  3. Does the source DB have limited capacity for ad-hoc queries? → Import (protect the source).
  4. Is there already a Power BI dataset in the Service that models this data? → Live Connection (don't duplicate work).
  5. Default for everything else → Import. It's faster, supports all DAX, and is far easier to maintain.
Import Mode — How VertiPaq Works

When you click Close & Apply in Power Query, Power BI loads your transformed data into VertiPaq — an in-memory columnar store that compresses data aggressively (often 5–10× smaller than the source). Integer and date columns compress best; high-cardinality text columns compress worst. This is why "remove unnecessary columns" is the highest-leverage model optimisation: every column you don't load is memory and refresh time you'll never pay.

DirectQuery Limitations to Know
  • Not all DAX functions are supported (time intelligence functions require special handling).
  • Maximum 1 million rows returned per visual.
  • Every visual on a page triggers a database query — heavy pages can slow significantly.
  • Row-Level Security definitions work differently.
  • You cannot create calculated tables or certain calculated columns.
🔧 Analogy — Grocery Shopping vs. Restaurant

Import = buying groceries and cooking at home. You do the work upfront (refresh = shopping trip), but once the ingredients are in your kitchen, meal prep is instant. The food is only as fresh as your last shop.

DirectQuery = eating at a restaurant. Every meal is prepared to order from fresh ingredients — always current — but you wait longer and the kitchen (source DB) gets busier when you have a large table.

Live Connection = ordering from a meal-kit delivery service. Someone else already designed the menu (the upstream model); you just plate and serve.

📊 RR EngineerWorks: Choosing the Mode
TableMode choiceReason
Fact_Orders (Excel, 600 rows)ImportSmall, fast, supports all DAX
Fact_Production (288 rows)ImportSmall, refreshed nightly
All Dim_ tablesImportDimension tables are always Import in star schemas
Targets_WideImportFinance updates monthly — a refresh is fine
Hypothetical: live IoT sensor stream (millions of rows/day) DirectQuery Volume too large to import; real-time reading required
⭐ Key Takeaway

Default to Import. It is faster, supports all DAX, and is much easier to optimise. Switch to DirectQuery only when data freshness or volume genuinely requires it — not because it feels more real-time.

Industry Use Cases for Data Connection

Why This Topic Exists

Before you connect anything, you should be able to sketch on a whiteboard what sources exist, where they live, and what refresh cadence is acceptable. This prevents the most expensive Power BI mistake: building a beautiful report and then discovering that the critical data source requires a Gateway you haven't set up, or that a needed column doesn't exist in the export.

Industry / Domain Typical Sources Key Connectors Typical Refresh Cadence
Manufacturing & Operations ERP (SAP/Oracle), MES, IoT sensors, quality inspection logs SAP BW, SQL Server, OData, REST API Hourly to daily (sensor data: streaming)
Sales & CRM Salesforce, Dynamics 365, HubSpot, territory/target spreadsheets Salesforce, Dynamics, SharePoint, Excel Daily; pipeline reports sometimes hourly
Finance & Accounting ERP GL exports, budget Excel files, bank reconciliation CSVs Excel, CSV, Azure SQL, SQL Server Monthly close + daily actuals
Project Management Project Online, Azure DevOps, Planner, Jira, status Excel trackers Project Online, OData, REST API Daily; sprint reviews weekly
HR & Workforce HRIS (Workday, SAP HR), payroll exports, org chart data OData, SQL Server, Excel CSV export Weekly; monthly for headcount planning
Supply Chain WMS, inventory databases, supplier portals, logistics APIs SQL Server, REST API, SharePoint Daily to real-time
💡 The Data Source Inventory

On any new project, before opening Power BI Desktop, create a simple spreadsheet with four columns: Source Name, Location / Server, Auth Type, Refresh Frequency Needed. This 15-minute exercise prevents 90% of "it worked on my machine but not in the Service" problems.

⭐ Key Takeaway

Every industry has the same underlying pattern: transaction fact tables in a database or ERP, dimension/lookup tables in a master data system, and plans/targets in finance spreadsheets. Recognising this pattern means you can scope a data connection plan in minutes.

Source Settings, Credentials & Privacy Levels

Credentials

Every data source in Power BI is associated with stored credentials. When you connect to a source for the first time Desktop prompts you to choose an authentication method. Desktop stores these credentials in File → Options → Data Source Settings. Each source can use one of the following:

Auth MethodUse WhenCommon Connectors
WindowsOn-premises SQL Server, file shares on your networkSQL Server, Analysis Services, Oracle
Database (SQL Auth)SQL login with a username/password specific to the DBSQL Server, MySQL, PostgreSQL
Microsoft Account (OAuth)Cloud Microsoft servicesSharePoint Online, OneDrive, Dataverse, Dynamics
API Key / Bearer TokenThird-party REST APIsWeb connector, OData, custom APIs
AnonymousPublic data; no auth requiredPublic OData, some web pages
Privacy Levels — Why They Exist

When Power Query merges two queries from different sources, it may fold the query logic so that data from Source A is sent to Source B's server as part of a native query. If Source A is a confidential internal DB and Source B is a public web API, you do not want internal row values being transmitted externally. Privacy levels prevent this.

LevelMeaningCan be combined with
PublicData is freely accessible; no sensitivityAnything
OrganizationalData is safe to share within the organisationOther Organizational or Public sources
PrivateData is confidential; isolate from other sourcesNothing (prevents cross-source query folding)
None (not set)Desktop asks you each time you combine sources—

Practical advice: For most internal enterprise projects, set all sources to Organizational. This eliminates the "Formula.Firewall" error that appears when you try to merge queries from sources with unset or mismatched privacy levels.

⚠ Common Error: Formula.Firewall

If you see Formula.Firewall: Query 'XYZ' (step 'Source') references other queries or steps, so it may not directly access a data source. Please rebuild this data combination — the fix is almost always to open File → Options & Settings → Options → Privacy → Always ignore Privacy Level settings (for personal use) OR to correctly set privacy levels on all sources to Organizational. Never set levels to None in a production report.

🔧 Analogy — Office Building Access Cards

Different floors in a building require different access levels. The lobby is public (anyone can enter). The open-plan office is organisational (employees only). The server room is private (only authorised IT staff). Privacy levels work the same way: data that lives on the "private floor" cannot be combined with anything from outside without your explicit knowledge.

📊 RR EngineerWorks Credentials Plan

For the handbook dataset (all from one local Excel file), credentials are handled automatically — no sign-in needed. In a real enterprise deployment:

  • Fact_Orders (SQL Server, on-prem): Windows auth → privacy = Organizational
  • Targets_Wide (SharePoint Online): Microsoft Account (OAuth) → privacy = Organizational
  • Currency Rates (public web API): Anonymous → privacy = Public

Setting all three to Organizational lets Power Query merge them without triggering Formula.Firewall.

⭐ Key Takeaway

Set privacy levels to Organizational for all internal sources from the start. Leaving levels unset is the most common cause of the Formula.Firewall error, and fixing it after you've built twenty queries is painful.

Handling Import Errors & Data Type Issues

Definition

Import errors occur when Power BI cannot read a source, or when it reads the data but assigns wrong types or flags rows as errors. These are not bugs — they are information: the source data has a quality problem, the path has changed, or the auth has expired.

Error / Symptom Cause Fix
File not found / path error File moved, renamed, or on a network drive that changed Power Query → right-click query → Edit source settings → update path. Or use a query parameter for the file path.
Column changed type → errors in rows Power BI auto-detected a column as Int64 but some rows contain text (e.g. "N/A") Remove the auto-type step → replace error values → then re-apply the correct type.
Duplicate column headers CSV export has two columns both named "Value" Power BI appends .1, .2. Rename in Power Query or fix at the source.
Encoding issues (garbled characters) CSV file saved in Windows-1252 but opened as UTF-8 In Power Query, right-click the source step → change encoding to Windows-1252 or the correct code page.
File locked (Excel in use) Someone has the source Excel open while refresh runs Use a read-only connection or copy the file to a staging folder before refresh.
Sign-in / credentials expired OAuth token expired in the Service Open the dataset in the Service → Settings → Data source credentials → re-authenticate.
Privacy level error (Formula.Firewall) Two sources have mismatched or unset privacy levels Set all source privacy levels to Organizational in Data Source Settings.
The Auto-Type Change Problem

By default, Power Query applies a "Changed Type" step automatically when you load any file. This is often helpful but can cause cascading errors if the source has messy data. In the RR EngineerWorks dataset you'll see this clearly: Fact_Production.PlannedUnits has ~105 rows stored as text strings. Power Query's auto-type step will flag those rows as Error when it tries to convert them to Int64.

The professional pattern is: delete the auto-type step → clean/standardise the column → then apply the correct type manually. This gives you control over what happens at each stage.

🔧 Analogy — Parcel Delivery Scanner

A warehouse scanner tries to read every barcode as it passes. If a barcode is smudged or printed in the wrong format, the scanner flags it as an error and routes it to a manual inspection station. Power Query does the same: rows that don't match the expected type are flagged as errors and isolated — they don't silently corrupt the rest of the table. Your job is to check the inspection station and decide: fix the format, replace with a default, or remove the row.

⭐ Key Takeaway

Import errors are not failures — they're diagnostics. Every error cell in Power Query is telling you exactly what's wrong and where. The worst outcome is not the error; it's ignoring it and loading a table where 30 rows silently became null.

Naming Conventions for Queries, Columns & Tables

Why Names Matter More Than You Think

In Power BI, the names you give your tables and columns appear in three places simultaneously: the Fields pane (what report builders see), the DAX formula bar (what you type every time you write a measure), and the visual tooltips (what the end user reads). A column called Column7 from an auto-detected Excel import causes confusion in all three places.

Good names are the highest-leverage, lowest-effort investment in your model's maintainability. Do them right at the Power Query stage, before the model, before DAX — changing a column name later cascades into every measure that references it.

Object Convention Example Avoid
Query / Table Prefix Fact_ or Dim_; PascalCase; no spaces Fact_Orders, Dim_Products Sheet1, orders data, tbl_1
Column TitleCase; spaces are fine for readability in the Fields pane; no special chars except underscore Order Date, Product Code, Total Amount OrderDate2, col_A, Value (GBP)
Measure Verb-phrase format; include unit where ambiguous Total Sales GBP, Sales vs Target %, YTD Revenue Measure1, Sales (ambiguous), calc
Parameter PascalCase with descriptive prefix FilePath_Orders, StartDate p1, param
Measure Table Use a non-data table prefix to float it to the top of the Fields pane _Measures or ⚙ Key Measures Scattering measures across fact tables
The Rename-on-Load Rule

Rule: Rename every query and every column at the Power Query stage — before you click Close & Apply. Never rename columns in the Model view after loading, because that breaks any measures already written against the old name.

In the lab you're about to do, the first transformation step on every table will be renaming: the query itself (from "Sheet Name" to the proper Fact_ / Dim_ name) and any columns with unclear auto-generated names.

📊 RR EngineerWorks: Before vs. After Naming
Default name (Excel import)Renamed to (Power Query)Why
Fact_Orders (already good)Fact_OrdersMatches convention — no change needed
Targets_WideTargets_Wide → after unpivot becomes Fact_TargetsAfter transformation, it's a proper fact table
HR_DirectoryHR_DirectoryKeep as-is but flag as disconnected in notes

⭐ Key Takeaway

Five minutes spent renaming queries and columns in Power Query saves hours of confusion in DAX and the Fields pane. The rename step should be the first Applied Step you add to every query, before any filtering or type changes.

Lab 2A — Connect & Load All 8 Sheets
Estimated time: 20 minutes  |  Requires: RR_EngineerWorks_Dataset.xlsx
1
Open your saved .pbix file

Open RR_EngineerWorks_v1.pbix that you saved in the Module 1 lab. If you don't have it, open Power BI Desktop and create a new blank file — File → New.

2
Open Get Data → Excel Workbook

In the Home ribbon click Get Data → Excel Workbook. Navigate to wherever you saved RR_EngineerWorks_Dataset.xlsx and click Open.

The Navigator dialog opens. You will see a folder icon for the workbook with 8 sheets listed below it.

3
Preview each sheet individually before selecting

Click each sheet name (without ticking the checkbox) to preview its data in the right panel. Look for:

  • Dim_Regions — 10 clean rows. Columns: RegionID, RegionName, Territory, Country, RegionalManager. Note the clean R01–R10 ID format.
  • Dim_Products — 30 rows. Spot the Category_SubCategory column — it contains values like Electronics|Sensors. One column, two pieces of information — it needs splitting.
  • Dim_Customers — 80 rows. Look at the ContactName column — you'll see JAMES WHITFIELD, anita desai, and Robert Marshall in the same column. Mixed casing. Also check Phone — several blank entries.
  • Fact_Orders — 600 rows. Look at OrderDate — some values appear as dates, others as text strings (01/05/2024, 2024-05-01). Look at ProductCode — spot prd-001, PRD001 mixed in with PRD-001. Look at CustomerID — values include C001 (correct format), CUST-001 (wrong prefix), and bare integers like 1. Look at RegionID — some blank cells.
  • Fact_Production — 288 rows. Look at PlannedUnits and ActualUnits — in the preview you'll see a mix of numbers and text strings like "340".
  • Targets_Wide — 10 rows. The structure is completely different — RegionName followed by 12 columns named Jan_2024, Feb_2024, etc. This is wide format — it needs unpivoting.
  • HR_Directory — 45 rows. Scan the columns: EmployeeID, FullName, Department, JobTitle, HireDate, AnnualSalary_GBP, ManagerName, OfficeLocation. Notice there is no RegionID, no CustomerID, no ProductCode. This table has no column that joins to any other table.
  • Dim_Date — 5 rows. This is a scaffold only — a template showing what your date table should look like. You will replace it with a full CALENDARAUTO-generated table in Module 6.
4
Select all 8 sheets and click Transform Data

5
Set the privacy level for the Excel file

Lab 2B — Explore Power Query Editor & Build Your Issues Log
Estimated time: 30 minutes  |  No transforms applied yet
1
Orient yourself in Power Query Editor

Power Query Editor has four key areas:

  • Queries pane (left) — all your loaded queries listed. Right-click any query to rename, duplicate, reference, or enable/disable load.
  • Data preview (centre) — shows the first 1,000 rows of the selected query. Column headers show the detected data type icon — click the icon to change it.
  • Applied Steps (right) — every transformation in sequence. Power BI auto-creates a Source and Changed Type step. You can click any step to preview the data at that point in time.
  • Formula bar (top) — shows the M code for the selected Applied Step. You can edit it directly.
2
Enable Column Quality and Column Distribution on every table

In the View ribbon, tick both:

  • Column Quality — shows % Valid, % Error, % Empty bars under each column header
  • Column Distribution — shows a mini bar chart of value frequency; flags distinct vs. unique counts

Keep these on for all labs from now on. They are the fastest way to spot data quality issues without scrolling through thousands of rows.

3
Inspect Fact_Orders — document every issue

Click Fact_Orders in the Queries pane. With Column Quality on, note what you see:

  • OrderDate: Column type icon shows ABC (text) rather than a calendar icon — it's been read as text, not dates. Column Distribution shows multiple distinct formats.
  • CustomerID: Column Distribution shows far more distinct values than the 80 customers in Dim_Customers. Inspect the values — you will see C001 (correct format), CUST-001 (wrong prefix), and bare integers like 1. Approximately 22% of orders have a CustomerID that will not join to Dim_Customers as-is.
  • ProductCode: Column Distribution shows far more distinct values than the 30 products in Dim_Products — the casing variations (prd-001, PRD001) are being counted as separate values.
  • RegionID: Column Quality shows some Empty % — these are the null RegionIDs.
  • TotalAmount: Scroll through — you won't easily spot the miscalculated rows visually, but you'll verify them in Module 3 by adding a custom column.
  • SalesRepName: Column Distribution shows some values with extra leading spaces — those count as separate entries from the clean versions.

Also check for duplicates: Home → Keep Rows → Keep Duplicates (note the count, then Ctrl+Z to undo — don't keep this step). You should see approximately 30 rows — Power Query keeps both copies of every duplicate pair, so 15 duplicate pairs produce 30 flagged rows. Ctrl+Z to undo before continuing.

4
Inspect Dim_Customers, Fact_Production, Targets_Wide, HR_Directory

Click each in turn and record what you observe:

  • Dim_Customers → ContactName: Column Distribution shows UPPERCASE and lowercase variants of the same names as separate values.
  • Dim_Customers → City: Same casing problem — LONDON, london, and London are three different values in the column distribution.
  • Dim_Customers → Phone: Column Quality shows ~25% Empty.
  • Fact_Production → PlannedUnits & ActualUnits: Data type icon shows ABC text. Column Quality will show Error % after the auto-type step tried to convert text strings to numbers.
  • Targets_Wide: The query has 13 columns — RegionName plus 12 month columns. This wide structure cannot be modelled with a date table. Note the column names: Jan_2024, Feb_2024, etc.
  • HR_Directory: Confirm there is no RegionID, no CustomerID, no ProductCode column. The only potential join candidate is ManagerName — but it's free text and doesn't match any column in any other table.
