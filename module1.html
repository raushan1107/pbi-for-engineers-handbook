Business Intelligence Concepts & Power BI's Role

Definition

Business Intelligence (BI) is a technology-driven process for collecting, structuring, and analysing business data in order to support faster, better-informed decisions. Power BI is Microsoft's end-to-end BI platform — it handles every stage of that process inside one connected toolset.

Why It Matters

Most organisations are not short of data — they're short of decisions backed by data. Teams export the same SQL table to Excel every Monday morning, manually paste it into a PowerPoint, and email it around. By the time the deck lands in the meeting room the numbers are already stale. And if anyone asks "what does this mean for EMEA specifically?" there is no answer — because the Excel file doesn't have that slice.

Power BI replaces that entire manual cycle with a refreshable, filterable, shareable analytics solution. The analyst stops being the person who runs the report and becomes the person who built the system that runs it automatically.

🔧 Analogy — Factory Control Room

Individual machines on a production floor generate readings — temperature, pressure, throughput rate — but those raw sensor values mean nothing until a central control panel synthesises them into a unified, actionable view. Power BI is that control panel for your business data. The machines are your data sources; the control panel is your semantic model and report canvas.

📊 RR EngineerWorks Example

RR EngineerWorks — the fictional manufacturing company used throughout this handbook — tracks sales orders in an Excel file, production output in a SQL Server database, regional targets in a SharePoint list, and headcount in a separate HR spreadsheet. A manager currently copies all four sources into a master workbook every Monday — a two-hour, error-prone process. By the end of Module 9 you will have a single Power BI report that refreshes these sources overnight and surfaces every KPI the business needs in seconds.

⭐ Key Takeaway

Power BI doesn't just chart data. It replaces an entire manual reporting workflow with a connected, refreshable, shareable analytics solution. The value is not in the charts — it's in eliminating the Monday-morning copy-paste.

The Power BI Ecosystem

Definition

Power BI is a family of tools, not a single application. Understanding which component does what is the difference between knowing where to build something and being confused about why it "looks different after I published it."

Component Role Where it lives
Power BI Desktop Connect to data sources, transform data (Power Query), build the semantic model, design report pages. This is where you spend 80% of development time. Free Windows app (powerbi.microsoft.com)
Power BI Service Publish, share, schedule refresh, manage security, collaborate in workspaces, create dashboards. The cloud platform your audience uses. app.powerbi.com (browser)
Power BI Mobile Consume reports and dashboards on the go. Optimised views for phones and tablets. iOS, Android, Windows apps
On-premises Data Gateway Bridges the Service to data sources that live inside your corporate network — SQL Server, local files, SharePoint on-prem. Required for scheduled refresh of on-prem data. Software installed on a server in your network
Workspaces Shared folders in the Service for team collaboration. Contains reports, datasets (semantic models), dashboards, and dataflows. Power BI Service
Dashboards Single-page pin-boards assembled from tiles taken from multiple reports. Great for at-a-glance executive views. Created in the Service, not Desktop. Power BI Service
Reports Multi-page, interactive documents built in Desktop and published to the Service. The primary deliverable in this course. Desktop (build) → Service (publish)
Why It Matters

The most common confusion in Power BI is caused by not knowing which component owns which capability. For example: you cannot create Row-Level Security roles in the Service (you define them in Desktop). You cannot pin visuals to a Dashboard from Desktop (only from the Service). A quick mental map prevents hours of frustrated searching.

🔧 Analogy — Professional Publishing Workflow

Think of Desktop as your InDesign workspace — where you write, design, and lay things out. The Service is the online publication platform — where readers access the finished work. Mobile is the reader's phone app. The Gateway is the secure content-sync bridge that keeps your local asset files in sync with the platform overnight.

📊 RR EngineerWorks Example

You will build the entire RR EngineerWorks analytics solution in Desktop throughout Modules 2–8. In Module 9 you will publish it to the Service, configure a nightly scheduled refresh via the Gateway (because the SQL Server production data is on-premises), and create an App so the management team receives a clean, read-only view of the reports.

⭐ Key Takeaway

Desktop = Build. Service = Share. Mobile = Consume. Gateway = Refresh on-premises data. Memorise this. Most "why isn't this working?" questions answer themselves once you know which tool owns which action.

3

Architecture & Data Flow

Definition

The Power BI data flow describes the journey that raw data makes from its original source to the end user's screen. It has five distinct stages, each with its own tool and purpose:

#StageToolWhat happens here
1 Data Sources External systems Raw data lives here — Excel files, SQL Server tables, SharePoint lists, APIs, cloud databases.
2 Power Query (ETL) Desktop Extract, Transform, Load. Remove duplicates, fix date formats, unpivot tables, split columns, merge queries. Data is cleaned before entering the model.
3 Semantic Model Desktop The in-memory model. Tables are connected with relationships, hierarchies are defined, DAX measures are created. This is the "single source of truth."
4 Report Canvas Desktop Visuals — charts, cards, tables, maps, slicers — built on top of the model. Interactivity is configured here (drill-down, tooltips, bookmarks).
5 Power BI Service Service / Gateway Published reports consumed by stakeholders. Refresh is scheduled, Row-Level Security is assigned, dashboards and Apps are created.
Why It Matters

Understanding the pipeline tells you where to look when things go wrong. Wrong row count in a visual? Is the problem at the source, in Power Query, or in a DAX measure? Slow report? Is it the data volume, the model design, or the visuals? A pipeline mental model lets you diagnose in minutes rather than hours.

It also tells you where to fix problems. The golden rule: fix data quality issues at the earliest possible stage. A missing column that can be added to the SQL view is better addressed at Stage 1 than patched with a DAX workaround at Stage 3.

🔧 Analogy — Water Treatment Plant

Raw water (source data) enters the plant → passes through filtration and treatment stages (Power Query) → is stored in clean holding tanks (semantic model) → piped to homes as clean, drinkable water (visuals and reports) → metered and billed (Service analytics and governance).

If the water at the tap smells, you don't fix the tap — you investigate the treatment stage or the source. Same principle applies in Power BI.

📊 RR EngineerWorks Data Flow

Stage 1 — Sources: Fact_Orders.xlsx, SQL Server production DB, SharePoint targets list, HR spreadsheet.

Stage 2 — Power Query: Fix inconsistent date formats in Fact_Orders, unpivot Targets_Wide (months as columns → rows), remove duplicate order rows, trim customer name casing.

Stage 3 — Semantic Model: Star schema — Fact_Orders at centre, surrounded by Dim_Products, Dim_Customers, Dim_Regions, Dim_Date. DAX measures for Total Sales, Sales vs Target, YTD Revenue.

Stage 4 — Report Canvas: Sales Performance page, Production Overview page, Management Summary page with drill-through and bookmarks.

Stage 5 — Service: Published to "RR EngineerWorks" workspace. Nightly refresh via Gateway. Row-Level Security by region for regional managers.

⭐ Key Takeaway

Power BI is a pipeline. A mistake at any stage propagates into every stage downstream. Fix problems at their source — always. The five stages also map directly to the five-step analytics workflow introduced in the next topic.

4

The Analytics Workflow: Explore → Transform → Model → Visualize → Publish

Definition

The five-stage analytics workflow is the repeatable process that structures every module in this handbook. It is also the sequence you will follow for every new Power BI project in your career:

StageQuestion you're answeringToolCovered in
1. Explore What data do I have? What's wrong with it? What am I trying to answer? Desktop — Navigator, Data preview Modules 1–2
2. Transform How do I clean and reshape the data into analysis-ready form? Desktop — Power Query Editor Module 3
3. Model How do these tables relate to each other? What calculations do I need? Desktop — Model view, DAX Modules 4–6
4. Visualize How do I present the answers clearly for my audience? Desktop — Report canvas Modules 7–8
5. Publish How do I share this, keep it fresh, and protect sensitive data? Service + Gateway + Desktop (RLS) Module 9
Why This Structure Matters

Most Power BI problems are caused by skipping stages. Jumping to Visualize before the model is solid means re-building report pages every time a relationship changes. Ignoring data quality in Explore means DAX measures that work in some filters and silently return wrong numbers in others.

This workflow is a forcing function: each stage has clear inputs and clear outputs. You don't start Modelling until Transformation is complete and verified. You don't start Visualising until the model answers your business questions correctly in the Data view.

🔧 Analogy — Building a House

Explore = survey the land and draw up requirements with the client. Transform = pour the foundation and frame the structure. Model = run the electrical and plumbing. Visualize = interior design, fixtures, finishes. Publish = open the doors to the occupants.

You cannot hang wallpaper if the walls aren't built yet. And you don't want to discover the plumbing is in the wrong place after the tiles are laid.

📊 RR EngineerWorks Workflow Map

Here is exactly how this handbook maps to the workflow for the RR EngineerWorks project:

  • Explore: Modules 1–2 — understand the business context and connect to all 8 source tables.
  • Transform: Module 3 — clean Fact_Orders, unpivot Targets_Wide, fix HR_Directory join key.
  • Model: Modules 4–6 — build the star schema, write DAX measures, add time intelligence.
  • Visualize: Modules 7–8 — Sales, Production, and Management report pages with AI analytics.
  • Publish: Module 9 — workspace, scheduled refresh, RLS by region.
  • Capstone: Module 10 — run the full workflow end-to-end on a scenario of your choice.
⭐ Key Takeaway

Speed in Power BI comes from doing each stage properly the first time, not from rushing to get something on the canvas. A well-modelled dataset takes twenty minutes to visualise. A poorly-modelled one takes days to patch.

Lab 1A — Power BI Desktop Orientation
Estimated time: 20 minutes  |  No data source needed yet
1
Install Power BI Desktop (if not already installed)

Open the Microsoft Store on your Windows machine, search "Power BI Desktop", and click Install. Alternatively, go to powerbi.microsoft.com → Downloads → Power BI Desktop and run the installer. The app is free — no licence required for this course.

Version check: Open Desktop → click Help in the ribbon → About. You should see a build from 2024 or later. If yours is older than 12 months, update it — some features in later modules (AI visuals, visual calculations) require a recent build.

2
Launch Power BI Desktop and dismiss the splash screen

On first launch you'll see a splash/welcome screen offering to connect to a sample dataset or sign in. Click the ✕ in the top-right corner of the splash screen to close it. You are now looking at an empty Power BI Desktop canvas.

Sign in (optional for this module): You do not need to sign in until Module 9 when you publish to the Service. You can skip the sign-in prompt for now.

3
Tour the three views — Report, Data, and Model

Look at the left-side icons — three stacked icons that switch between Desktop's three main views:

  • Report view (page icon) — The default view. This is the canvas where you drag and drop visuals, configure filters, and design report pages. Think of it as the "front end."
  • Data view (table icon) — Shows the actual data rows in each loaded table. Use this to verify that transformations worked correctly and that calculated columns contain expected values. It is empty until you load data.
  • Model view (diagram icon) — A diagram of all loaded tables and the relationships between them. This is where you build your star schema. Also empty until data is loaded.

Click each icon now to switch between them and get a feel for the layout.

4
Identify the key panes in Report view

Switch back to Report view. On the right side you will see two panels:

  • Visualizations pane — All available chart types. Click a visual type to add it to the canvas. Below the chart icons you will see Build visual, Format visual, and Analytics tabs — these appear once a visual is selected.
  • Data (Fields) pane — Lists every table and column in your model. After you load data, you drag fields from here into the Visualizations pane to populate charts.

On the left side you will see Filters pane — page-level, report-level, and visual-level filters go here.

5
Explore the ribbon — Home, Insert, Modelling, View, Optimize, Help

The ribbon at the top mirrors the workflow stages:

  • Home — Where you start: Get Data, Transform Data (opens Power Query), Publish.
  • Insert — Add text boxes, images, buttons, shapes to report pages.
  • Modelling — Create measures, calculated columns, calculated tables; manage relationships; set up RLS roles.
  • View — Toggle panes, switch themes, enable the Performance Analyzer.
  • Optimize — Performance mode settings (introduced in 2024 builds).
  • Help — Version info, links to documentation, guided learning.
6
Do a first-look preview of the RR EngineerWorks dataset (Navigator only)

Now load a preview of the dataset without applying any transforms. Click Home → Get Data → Excel Workbook. Navigate to the downloaded RR_EngineerWorks_Dataset.xlsx file and click Open.

The Navigator dialog opens. You will see a folder tree of all sheets in the workbook. Click each sheet name to preview its data in the right pane. Do not check any boxes yet — we are looking only.

As you browse, look for the following deliberate issues (you'll fix these in Module 3):

  • Fact_Orders — mixed date formats in the OrderDate column (some DD/MM/YYYY, some YYYY-MM-DD). Inconsistent product code casing (PRD-001 vs prd-001). A few obvious duplicate rows.
  • Targets_Wide — months as separate columns (Jan_2024, Feb_2024, …) rather than rows. This wide format cannot join to a date table.
  • HR_Directory — uses ManagerName (free text) instead of an employee ID. There is no numeric key that links to any other table — this table is intentionally disconnected.
  • Dim_Products — a combined Category_SubCategory column that needs splitting.

Once you have browsed all 8 sheets, click Cancel (not Load). We will return to this dialog properly in Module 2.

7
Save your file as a starting point

Click File → Save. Name the file RR_EngineerWorks_v1.pbix and save it to C:\PBI4Engineers\ (or wherever you prefer). This empty file will be your starting point for Module 2.

Note: A .pbix file contains the entire Power BI project — data model, visuals, queries, and report pages — in a single portable file. Think of it as your "project file."
