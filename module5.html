DAX Foundations

DAX (Data Analysis Expressions) is the formula language of Power BI. It looks like Excel formulas but operates fundamentally differently — every DAX expression is evaluated inside a filter context set by the report visual, not by a cell position on a grid. Understanding this distinction is the key that unlocks everything else in DAX.

DAX Syntax & Concepts

What DAX Is

DAX is a functional expression language — every expression returns a value (a scalar, a table, or a column). There are no loops, no variables declared in the traditional sense (though VAR exists), and no imperative control flow. You write an expression that describes what to compute; Power BI determines when and how many times to compute it based on what the visual needs.

Identifiers

Column references use the form 'TableName'[ColumnName]. The quotes around the table name are required when the name contains spaces; they are optional (but harmless) otherwise. Measure references use just [MeasureName] — no table prefix. 

-- Column reference (required: table + column)
Fact_Orders[TotalAmount]

-- Measure reference (no table prefix)
[Total Sales]

-- When table name has a space, use single quotes
'Dim Customers'[CustomerID]   -- our tables don't have spaces, but good to know

Measures vs Columns vs Tables

Three Types of DAX Calculations
TypeReturnsEvaluatedStored in modelUse when
Measure A single scalar value At query time, in the current filter context No — recalculated on every visual update Aggregating data for a visual (Sum, Count, Ratio, etc.)
Calculated Column One value per row At model refresh time, row by row Yes — stored in memory like any other column Row-level classification, concatenation, lookup result stored per row
Calculated Table An entire table At model refresh time Yes — stored in memory like any other table Generating a Date table (CALENDARAUTO), creating lookup tables from formulas
The Golden Rule: Prefer Measures Over Calculated Columns

Calculated columns consume memory proportional to the number of rows. Measures compute on-the-fly and use compression. For any calculation that is an aggregation (sum, count, average, ratio), always use a measure. Only use a calculated column when you need a row-level value that will be used as a slicer, filter, or axis label — not as a numeric aggregate.

Common mistake: creating a calculated column for Profit = Revenue - Cost and then summing it in a visual. Better: create a measure Total Profit = SUM(Fact_Orders[TotalAmount]) - SUM(Fact_Orders[UnitCost]) (or reference other measures). The measure computes the same result but uses no storage.

Writing Your First Measures

The New Measure Dialog

To create a measure: select a table in the Fields pane (always select _Measures) → right-click → New measure. The formula bar opens with Measure = pre-filled. Replace the whole thing with your expression. Press Enter to commit.

To move an existing measure to _Measures: click the measure in Fields pane → in the Measure Tools ribbon, find Home Table and select _Measures from the dropdown.

Essential Aggregation Functions
FunctionWhat it doesExample
SUM(column)Sum of all values in a columnSUM(Fact_Orders[TotalAmount])
AVERAGE(column)Mean of all valuesAVERAGE(Fact_Orders[DiscountPct])
COUNT(column)Count of non-blank valuesCOUNT(Fact_Orders[OrderID])
COUNTROWS(table)Count of rows in the table (in current filter)COUNTROWS(Fact_Orders)
MIN(column) / MAX(column)Minimum / Maximum valueMIN(Fact_Orders[OrderDate])
DIVIDE(numerator, denominator [, alternate])Safe division — returns alternate (default BLANK) on divide-by-zeroDIVIDE([Total Sales], [Total Orders])
Why DIVIDE Instead of /

Using [Total Sales] / [Total Orders] will produce an error (and break visuals) whenever Total Orders is zero — for example, in a region that has no orders in the selected period. DIVIDE([Total Sales], [Total Orders]) returns BLANK() instead, which Power BI hides from visuals cleanly. Always use DIVIDE() for ratios.

Understanding Filter Context

What Filter Context Is

Every time Power BI evaluates a measure, it does so within a filter context — a set of filters that restrict which rows of the model are visible to that evaluation. The filter context is built automatically from:

  • Slicer selections on the report page
  • The row or column position in a matrix or table visual
  • Cross-highlighting from other visuals
  • Report-level or page-level filters

When you write SUM(Fact_Orders[TotalAmount]), it sums only the rows that survive the current filter context — not all 585 rows. If a slicer selects "North England" only, the filter flows through Dim_Regions → Fact_Orders (via the relationship) and SUM(Fact_Orders[TotalAmount]) returns only the sum for orders in that region.

Filter Context Flows Through Relationships

When a user selects "Sensors" from the Category slicer (which comes from Dim_Products), the filter flows from Dim_Products to Fact_Orders via the ProductCode relationship. Any measure on Fact_Orders is then calculated only for Sensor products — without any explicit JOIN or WHERE clause in your formula.

This is the core value of the semantic model: the relationships define how filters propagate, so your measures stay simple.

Row Context vs Filter Context

Row context is a separate concept — it exists when iterating over a table row by row (inside iterator functions like SUMX, AVERAGEX, or when computing a calculated column). Row context is the current row being evaluated; it does not automatically filter other tables. This distinction becomes important in Module 6 (Advanced DAX) when we use iterator functions.

CALCULATE & Context Modifiers

What CALCULATE Does

CALCULATE is the most important function in DAX. It evaluates an expression (any measure or aggregation) inside a modified filter context — you can add filters, remove filters, or replace filters. 

CALCULATE(
    <expression>,
    <filter1>,
    <filter2>,
    ...
)

The expression is evaluated after all the filter arguments have been applied on top of (or instead of) the current filter context.

Boolean Filter Arguments

The simplest CALCULATE filters are boolean expressions referencing a column: 

-- Count only Completed orders regardless of the visual's status filter
Completed Orders =
CALCULATE(
    COUNTROWS(Fact_Orders),
    Fact_Orders[OrderStatus] = "Completed"
)

-- Total sales from the Direct channel only
Direct Sales =
CALCULATE(
    [Total Sales],
    Fact_Orders[SalesChannel] = "Direct"
)

A boolean filter replaces any existing filter on that column. If a slicer already filters OrderStatus to "Pending", writing Fact_Orders[OrderStatus] = "Completed" inside CALCULATE overrides it — the result is always Completed orders.

ALL — Removing Filters

ALL(table_or_column) removes all filters from the specified table or column. This lets you compute a denominator that ignores the visual's current filter. 

-- Total sales ignoring any region filter (for use as denominator)
All Regions Sales =
CALCULATE(
    [Total Sales],
    ALL(Dim_Regions)
)

-- Each region's share of total sales
Region Sales % =
DIVIDE(
    [Total Sales],
    [All Regions Sales]
)

When a matrix shows regions in rows, [All Regions Sales] returns the same grand total in every row, making [Region Sales %] show each region's share correctly.
