Power Query Interface & Applied Steps

Definition

Power Query Editor is Power BI's built-in ETL tool. Every action you take — filtering, renaming, splitting, replacing — is recorded as an Applied Step in a sequential list on the right side of the editor. Each step is a line of M code (the language that Power Query compiles your clicks into) that you can read, edit, or delete.

The Four Panels
PanelLocationWhat it contains
Queries paneLeft All queries in the project. Right-click to rename, duplicate, reference, enable/disable load, or move to a group.
Data previewCentre First 1,000 rows of the current query at the selected Applied Step. Column headers show the detected data-type icon.
Applied StepsRight (Query Settings) Every transformation in order. Click any step to preview data at that point. The gear icon to the right of a step reopens its dialog for editing.
Formula barTop (toggle in View) Shows the M expression for the selected step. You can type M directly here — every UI action is just a shortcut for writing M.
Applied Steps: Your Audit Trail

Applied Steps are the most important concept in Power Query. They make your transformation pipeline transparent (every action is visible), reproducible (the same steps run on every refresh), and reversible (delete a step to undo it without affecting earlier steps).

This is fundamentally different from editing data directly in Excel — in Excel, there is no record of what you changed or when. In Power Query, every change is documented, dated, and repeatable.

The Auto-Type Step Problem

When you load any file, Power Query automatically adds two steps: Source (connects to the file) and Changed Type (guesses data types from the first few rows). The Changed Type step is helpful for clean data but dangerous for messy data — it will convert rows it can't parse into Error values.

Rule: For any table with data quality issues, delete the auto-generated Changed Type step first. Clean the data. Then add the correct type step manually at the end. This gives you control over which errors you handle and which you convert.

M Code: What's Happening Behind the Clicks

Every step you create via the ribbon has an M expression. For example, removing duplicate rows generates: 

= Table.Distinct(#"Previous Step Name", {"OrderID"})

You don't need to write M from scratch for most operations — but reading it tells you exactly what happened. In complex cases (mixed date formats, conditional logic) you'll need to edit M directly. The formula bar is where you do that.

🔧 Analogy — Recipe Card for Your Data

A recipe card lists every preparation step in order: "peel the onion → dice into 1cm cubes → sauté on medium heat for 5 minutes." You can follow the recipe exactly, swap out a step (dice → slice), or add a new step between existing ones. Applied Steps are the same thing for your data — an ordered recipe that runs every time the report refreshes, producing the same clean output from the same raw input.

⭐ Key Takeaway

Never edit data directly — always create a new Applied Step. The step list is your documentation, your undo history, and your refresh logic all in one. Delete the auto-type step on any messy table, clean first, type last.

Filter, Sort, Group, Replace & Remove Duplicates

Definition

These five operations cover the majority of row-level and value-level cleaning tasks. Together they can resolve most data quality issues in a fact table before a single column-level transform is needed.

OperationWhere to find itCommon use in RR EngineerWorks
Filter Rows Column header dropdown arrow → Text/Number/Date filters Remove cancelled orders from Fact_Orders if they should be excluded from analysis; remove test rows.
Remove Duplicates Home → Remove Rows → Remove Duplicates Eliminate the 15 duplicate OrderID rows in Fact_Orders. Always specify which columns define "duplicate" — usually the primary key.
Replace Values Transform → Replace Values (or right-click column) Standardise ProductCode formats (PRD001 → PRD-001); replace null RegionIDs with "Unknown".
Sort Column header dropdown → Sort Ascending/Descending Sort Fact_Orders by OrderDate before loading — makes the Data view easier to navigate and can improve compression slightly.
Group By Transform → Group By Aggregate production records to monthly summaries; count orders per customer for a customer-level fact table.
Remove Errors Home → Remove Rows → Remove Errors Last resort — remove rows where critical columns (e.g. OrderDate) could not be parsed. Better than silently loading nulls.
Remove Duplicates: Primary Key vs All Columns

"Remove Duplicates" by default checks all columns — two rows must be identical in every column to be considered duplicates. In Fact_Orders, the duplicate rows are exact copies, so this works. But the safer pattern is to select only the primary key column (OrderID) and remove duplicates on that alone. This way, two rows with the same OrderID but slightly different values (data-entry corrections) will still be caught.

To deduplicate on a specific column: Select the column header → Home → Remove Rows → Remove Duplicates. The generated M is: = Table.Distinct(#"Previous Step", {"OrderID"})

🔧 Analogy — Quality Control Inspector

A QC inspector on a production line doesn't rebuild faulty products — they filter them out, log them, and return clean units to the next station. Power Query's Remove Rows operations do the same: they isolate and remove bad data (duplicates, errors, blanks that shouldn't be there) so only clean rows pass through to the model.

⭐ Key Takeaway

Remove Duplicates on the primary key column, not all columns — it's more robust to minor data variations. Always check the row count before and after to confirm you removed the right number.

Column Operations: Split, Merge, Extract & Format

Definition

Column operations reshape data at the column level — splitting combined values into separate columns, formatting text for consistency, or extracting substrings. These are the most visible transforms because they change the shape of the table itself.

OperationHow to accessRR EngineerWorks use
Split Column by Delimiter Select column → Transform → Split Column → By Delimiter Split Category_SubCategory ("Electronics|Sensors") on "|" → creates Category and SubCategory columns.
Split Column by Character Transition Transform → Split Column → By Character Transition Split codes like "PRD001" where letters transition to digits — useful for inconsistent ID formats.
Merge Columns Select columns → Transform → Merge Columns Combine FirstName + LastName into FullName; build a composite key for matching.
Format: UPPERCASE / lowercase / Capitalize Each Word Transform → Format → (choose option) Fix City casing in Dim_Customers; standardise ContactName to Title Case.
Format: Trim Transform → Format → Trim Remove leading/trailing spaces from CompanyName and SalesRepName.
Format: Clean Transform → Format → Clean Remove non-printable characters (line breaks, tabs) that sometimes appear in CSV exports.
Extract Transform → Extract → (First N Characters, Last N, Between Delimiters, etc.) Extract year from a date-text like "2024-Q1-Data" without writing M manually.
Add Column from Examples Add Column → Column from Examples Type the expected output for a few rows and let Power BI infer the M formula. Excellent for tricky string patterns.
Splitting a Column: What Happens to Your Headers

When you split a column Power BI creates new columns named OriginalName.1, OriginalName.2, etc. Always rename these immediately — add a "Rename Columns" step right after every split. This keeps the Applied Steps list readable and prevents confusion when you return to the query weeks later.

The M code for a split on "|" looks like: 

= Table.SplitColumn(#"Previous Step", "Category_SubCategory",
    Splitter.SplitTextByDelimiter("|", QuoteStyle.Csv),
    {"Category", "SubCategory"})

Notice you can pass the target column names directly in the M code, skipping the manual rename step.

🔧 Analogy — Shipping Container Labelling

A shipping container arrives labelled "Electronics/Sensors/HighPressure" — three attributes jammed into one label. A dock worker peels off the combined label and replaces it with three separate, scannable labels. Split Column does the same: one overcrowded column becomes several clean, targeted columns that can be filtered, grouped, and joined independently.

⭐ Key Takeaway

Rename immediately after every Split. The auto-generated ColumnName.1 names will flow through every downstream step and make your Applied Steps unreadable. Rename as part of the same split transaction using M, or add a Rename step right after.

Appending & Merging Queries

Definition

Append stacks rows from two or more tables on top of each other (equivalent to SQL UNION ALL). Merge joins columns from a second table into the first based on a matching key (equivalent to SQL JOIN).

OperationAnalogyWhen to useWhen NOT to use
Append Queries Stacking pages of paper from two printers into one pile Combining monthly CSV exports into one fact table; unioning 2023 and 2024 orders after migrating to a new system. When the tables have different schemas or represent different entities — appending Fact_Orders and Dim_Products makes no sense.
Merge Queries (Left Outer) Looking up a part number in a catalogue to get its description Bringing a lookup value into a table for cleaning — e.g. adding RegionName to Fact_Orders so you can filter by name during QA. OR fixing a key mismatch by merging on a partially-matching column. When the join should live in the model as a Relationship — don't merge dimension data into fact tables for analytical purposes. Keep them separate and let DAX traverse the relationship.
Merge Join Types
Join TypeKeepsUse for
Left OuterAll rows from left table; matched rows from rightEnriching a fact table — keep all orders even if the product isn't in the catalogue
InnerOnly rows with a match in both tablesFiltering — keep only orders for products that exist in the master catalogue
Left AntiRows in left that have NO match in rightFinding orphan records — orders with ProductCodes not in Dim_Products
Full OuterAll rows from both tablesComparing two datasets to find gaps in either direction
💡 Merge vs. Model Relationship

Use Merge in Power Query when you need a value from another table for the purpose of cleaning (e.g. looking up the correct RegionID to fix a name mismatch). Use a Model Relationship when you need the connection for analysis (e.g. slicing sales by region). Merging for analysis creates a denormalised flat table that's harder to maintain and more memory-intensive.

⭐ Key Takeaway

Merge for cleaning; relate for analysis. A merge in Power Query is a permanent denormalisation. A model relationship is reversible, flexible, and memory-efficient.

Conditional Columns, Custom Columns & Column from Examples

Definition

These three tools let you add new columns to a table derived from existing columns. They differ in how you define the logic:

ToolLogic defined byBest for
Conditional Column Point-and-click if/else UI (no M required) Simple bucketing: "If ListPrice > 200 then 'Premium', else if > 50 then 'Mid-range', else 'Budget'"
Custom Column M expression you write in the formula box Complex calculations, date parsing, multi-condition logic, combining columns
Column from Examples You type expected values for a few rows; Power BI infers the M formula Tricky text patterns where you know the output but not the M syntax
Key Power Query Custom Column Patterns
// Text manipulation
= Text.Upper([ProductCode])                     // "prd-001" → "PRD-001"
= Text.Trim([CompanyName])                      // remove leading/trailing spaces
= Text.Proper([ContactName])                    // "JOHN SMITH" → "John Smith"
= Text.Replace([ProductCode], "PRD", "PRD-")   // "PRD001" → "PRD-001"

// Date parsing with mixed formats
= try Date.From([OrderDate])
  otherwise try Date.FromText([OrderDate], [Format="yyyy-MM-dd"])
  otherwise null

// Bucketing (equivalent to Conditional Column)
= if [ListPrice] > 200 then "Premium"
  else if [ListPrice] > 50 then "Mid-range"
  else "Budget"

// Build a first-of-month date from "Jan_2024"
= Date.From("01-" & Text.Replace([Attribute], "_", "-"))
Custom Column vs. Calculated Column (DAX)

This is a common point of confusion. The rule is simple:

  • Power Query Custom Column: Data is fixed when loaded. Use for cleaning, reshaping, building keys, parsing dates. Runs during refresh. Values are stored in the model.
  • DAX Calculated Column: Calculated in the model after load. Can access other tables via relationships. Use for business logic that depends on the model structure (e.g. a column that looks up a value from a related table).

If it's purely about reshaping or parsing the source data → Custom Column in Power Query. If it requires a relationship traversal or depends on filter context → Calculated Column in DAX.

⭐ Key Takeaway

Do as much column derivation as possible in Power Query — it runs during refresh, before the model is loaded, and avoids inflating the model's calculated column overhead. Keep DAX calculated columns for logic that genuinely requires relationship traversal.

Handling Nulls, Blanks & Errors

Definition — Three Different Things
ValueWhat it isShown in preview asColumn Quality shows
null Absence of value — the cell truly has no data null (italic) Empty %
Blank ("") An empty text string — a value IS present, it just contains nothing (empty cell — looks the same as null but isn't) Valid % (it IS a value)
Error A conversion or operation failed for this row Error (italic, red tint) Error %

This distinction matters because Replace Values only replaces null by default. A blank string ("") will not be caught by "Replace null with Unknown" — you need a separate step to handle blanks.

Handling Patterns
SituationToolM generated
Replace null with a fixed value Transform → Replace Values → tick "Replace null values" Table.ReplaceValue(…, null, "Unknown", Replacer.ReplaceValue, {"Column"})
Replace blank string with null Replace Values: Value to Find = "" (empty), Replace With = null Table.ReplaceValue(…, "", null, Replacer.ReplaceText, {"Column"})
Convert errors to null Right-click column → Replace Errors Table.ReplaceErrorValues(…, {{"Column", null}})
Remove rows with errors in a specific column Home → Remove Rows → Remove Errors Table.RemoveRowsWithErrors(…, {"Column"})
Fill down (propagate value through consecutive nulls) Transform → Fill → Down Table.FillDown(…, {"Column"})
The Correct Order for Type Conversion on Messy Columns
  1. Delete the auto-generated Changed Type step.
  2. Replace Errors → null (so error rows become visible, not invisible).
  3. Replace null with a meaningful default OR remove rows with null where appropriate.
  4. Clean and standardise the column values (trim, format, replace).
  5. Change Type to the correct final type (Int64, Date, Decimal, etc.).

Doing the type conversion last, after cleaning, means no cleaning step can reintroduce errors. The type step runs on already-clean values.

🔧 Analogy — Sorting Post at a Mail Room

A mail-room worker sorts incoming packages: packages with complete addresses go through (valid), packages with missing postcodes go to a "needs attention" tray (null/blank), and packages with illegible labels go to the errors pile. These are three separate handling processes, not one. Power Query treats nulls, blanks, and errors the same way — each needs its own handling rule.

⭐ Key Takeaway

null, blank, and Error are different values that need different fixes. Always check Column Quality (Empty % vs Error %) to know which you have before writing a replacement rule.

Data Profiling: Column Quality, Distribution & Profile

Definition

Data profiling is the practice of automatically analysing a column to understand its characteristics before you transform it. Power Query provides three views — accessible in the View ribbon — that turn hundreds of rows into a one-glance quality assessment.

Profiling ViewWhat it showsBest for detecting
Column Quality Three bars below each column header: Valid % (green), Error % (red), Empty % (grey) Null RegionIDs (Empty %), text strings in numeric columns (Error %), missing phone numbers
Column Distribution A frequency bar chart + Distinct count (number of different values) and Unique count (values that appear only once) Casing variants of the same value (LONDON / London / london = 3 distinct but should be 1); ProductCode format mix; unexpected values
Column Profile Detailed statistics for the selected column: min, max, average, standard deviation, value distribution table, null count Outlier values (a ListPrice of 0 that should be excluded); impossible dates; column cardinality
Profile Based on Entire Dataset

By default, Power Query profiles only the first 1,000 rows of your data. This is fast but misleading for large tables — a null at row 1,500 will not appear in the Column Quality bars, making you think the column is clean when it isn't.

Fix: Click the status bar text that says "Column profiling based on top 1000 rows" (bottom-left of the Power Query window) and switch to "Column profiling based on entire data set". Do this on every new project before any profiling.

For Fact_Orders (600 rows) the difference is minimal. For production datasets with millions of rows this switch is critical.

Reading Distinct vs. Unique Count

Column Distribution shows two counts above the chart:

  • Distinct: How many different values exist (including duplicates). ProductCode in raw Fact_Orders shows ~90 distinct values even though there are only 30 products — the casing variants inflate this count.
  • Unique: How many values appear exactly once. If Distinct ≠ Unique, there are repeated values. If Distinct = row count, every value is unique (good for primary key columns like OrderID — unless there are duplicates).

Query Parameters & Reusability

Definition

A query parameter is a named, typed variable that can be referenced anywhere in your Power Query M code. Instead of hardcoding a file path like "C:\Users\raushan\Downloads\...", you store it in a parameter called FilePath_Dataset and reference that parameter in your Source step. Change the parameter once → all queries that use it update automatically.

Creating a Parameter

Home → Manage Parameters → New Parameter. Give it:

  • Name: descriptive, PascalCase — e.g. FilePath_Dataset
  • Type: Text (for file paths), Date, Number, etc.
  • Current Value: the actual file path or value
  • Suggested Values: optionally list valid options

In the Source step M code, replace the hardcoded path with the parameter name: = Excel.Workbook(File.Contents(FilePath_Dataset), true)

Why Parameters Matter for Maintainability

When a colleague opens your .pbix file on their machine, or when you deploy to a different environment, the file path will be different. Without a parameter, every query that references the file needs to be updated manually. With a parameter, you update one value and everything refreshes.

Parameters are also used for incremental refresh (RangeStart / RangeEnd parameters), environment switching (dev vs prod database names), and what-if analysis (a threshold parameter that filters data above/below a value).

Query Groups — Organising Large Projects

In the Queries pane, right-click any query → Move to Group → New Group. Create groups like Fact Tables, Dimension Tables, Helper Queries, and Parameters. This keeps the Queries pane readable when you have 15+ queries.

⭐ Key Takeaway

Any hardcoded value that might change (file path, server name, date range) should be a parameter. It takes two minutes to create and saves hours of debugging when the environment changes.

Fix 2 — Standardise ProductCode format

The column contains PRD-001 (correct), prd-001 (lowercase), PRD001 (no dash), and Prd-001 (wrong case). We need everything as PRD-001.

Fix 3 — Standardise CustomerID format

The CustomerID column mixes three formats: C001 (correct), CUST-001 (wrong prefix), and bare integers like 1 (no prefix, no padding). All must normalise to C{NNN} so this column joins cleanly to Dim_Customers.CustomerID in Module 4.

Step A — Remove the "CUST-" prefix:
Select the CustomerID column → Transform → Replace Values → Value to Find: CUST- → Replace With: C → OK.
This converts CUST-001 → C001. ✓

Step B — Convert bare integers to C-format:
Add Column → Custom Column. Name it CustomerID_Fixed. Enter this expression: 

= if Text.StartsWith([CustomerID], "C")
  then [CustomerID]
  else "C" & Text.PadStart([CustomerID], 3, "0")

This leaves C001 unchanged, and converts 1 → C001, 23 → C023. ✓

Step C — Replace the original column:
Right-click the original CustomerID column header → Remove. Then double-click CustomerID_Fixed and rename it to CustomerID. Drag the column left to restore its original position (second column after OrderID), or use Transform → Move → To Beginning and then reorder.

Fix 4 — Fix OrderDate mixed formats

The OrderDate column contains three types of values: proper date objects, UK-format text strings (01/05/2024), and ISO text strings (2024-05-01). Power Query needs to be told which locale to use for the text strings.

Click the type icon (ABC) in the OrderDate column header → select Using Locale…

In the dialog: Data Type = Date, Locale = English (United Kingdom) → OK.

This tells Power Query that 01/05/2024 means 1 May 2024 (DD/MM/YYYY, UK) not January 5th (US). ISO format (2024-05-01) is parsed correctly regardless of locale.

After this step: Column Quality should show 100% Valid (green) on OrderDate. The type icon should change to a calendar icon.

Fix 7 — Verify and recalculate TotalAmount

Replace the original column:

  • Right-click the TotalAmount column header → Remove
  • Double-click TotalAmount_Correct → rename to TotalAmount

All subsequent modules will use this recalculated, correct value.

DefectRate_Pct: Decimal Number

For ProductionMonth (stored as text like "2024-01-01"): click the type icon → Date. ISO-format strings (YYYY-MM-DD) are unambiguous and need no locale setting.

Lab 3F — Unpivot & Reshape Targets_Wide → Fact_Targets
~25 minutes  |  The conceptually richest transformation in this module

The problem: Targets_Wide has months as columns (Jan_2024, Feb_2024, …). This wide format cannot be related to a date table — there is no single "Month" column to join on. We need to reshape it to tall format: one row per region per month, with a single Month column and a single TargetAmount column. This operation is called Unpivot.

1
Rename the query from Targets_Wide to Fact_Targets

Right-click Targets_Wide in the Queries pane → Rename → type Fact_Targets → Enter.

After transformation this will be a proper fact table — one row per region per month — so the Fact_ prefix is correct.

2
Delete the auto Changed Type step

Delete the Changed Type Applied Step.

3
Select RegionName and Unpivot Other Columns

Click the RegionName column header to select it. Then: Transform → Unpivot Columns → Unpivot Other Columns.

This tells Power Query: "Keep RegionName fixed. Turn every other column (Jan_2024, Feb_2024, …) into rows."

Result: The table goes from 10 rows × 13 columns to 120 rows × 3 columns: RegionName, Attribute, Value.

The Attribute column contains "Jan_2024", "Feb_2024", etc. The Value column contains the target amounts.

4
Rename Attribute → Month and Value → TargetAmount

Double-click Attribute → rename to Month.

Double-click Value → rename to TargetAmount.

5
Build a Date column from the Month text

The Month column contains "Jan_2024". We need a proper date (first of each month) to join against the date table later.

Add Column → Custom Column. Name it MonthStart. Enter this expression: 

= Date.From("01-" & Text.Replace([Month], "_", "-"))

This turns "Jan_2024" into "01-Jan-2024" and then converts it to a Date: 01/01/2024.

Change the MonthStart column type to Date.

6
Fix the RegionName mismatch

Column Distribution on RegionName shows "Europe - International" as one of the 10 region names. In Dim_Regions, the equivalent entry for R09 is simply "Europe". The mismatch is the dash-and-descriptive suffix in Targets_Wide vs. the plain regional name in Dim_Regions.

These two tables will need to join on RegionName in Module 4. Fix the mismatch now so the join works:

Transform → Replace Values
Value to Find: Europe - International
Replace With: Europe
→ OK.

Verify: Fact_Targets.RegionName should now contain exactly the same 10 distinct values as Dim_Regions.RegionName (North England, South England, East England, West England, Midlands, Scotland, Wales, Northern Ireland, Europe, Rest of World).

7
Set column types and verify

RegionName, Month: Text
TargetAmount: Whole Number (or Decimal if targets have decimal precision)
MonthStart: Date (already set in Step 5)

Verify: 120 rows (10 regions × 12 months), MonthStart column shows proper dates from 2024-01-01 to 2024-12-01.

💡 What Unpivot Actually Does

Before unpivot (wide — 1 row per region):

RegionNameJan_2024Feb_2024Mar_2024
North England95,00088,000102,000

After unpivot (tall — 1 row per region per month):

RegionNameMonthTargetAmount
North EnglandJan_202495,000
North EnglandFeb_202488,000
North EnglandMar_2024102,000

The tall format is the only one that can join to a date dimension table and produce correct time intelligence calculations.

Lab 3G — The Disconnected Table Decision (HR_Directory)
~10 minutes  |  An important design decision, not a technical fix
1
Confirm the disconnection

Click HR_Directory. Review the columns: EmployeeID, FullName, Department, JobTitle, HireDate, AnnualSalary_GBP, ManagerName, OfficeLocation.

None of these columns match a primary or foreign key in any other table. OfficeLocation is a city name — it could partially match Dim_Customers.City, but that join would be meaningless. ManagerName is free text with no equivalent in any other table.

This is a genuinely disconnected table. It cannot be meaningfully related to the sales or production model without additional data (such as a SalesRep-to-EmployeeID mapping table).

2
The three options — choose one

For a disconnected table you always have three choices:

OptionWhen to useHow
A — Exclude from model load The table is irrelevant to current analysis. Keep the query for documentation but don't load it. Right-click query → uncheck Enable Load. Query stays in Power Query Editor but doesn't appear in Data or Model view.
B — Fix the join key A mapping table exists (or can be created) that links EmployeeID to SalesRepName. Create a mapping table query → Merge HR_Directory on EmployeeID → use the matched SalesRepName as the join key.
C — Use as a standalone report table HR wants its own HR reports that don't cross with sales data. Load it as a standalone table — it creates no relationships but can be used in visuals that only show HR data.
3
Apply Option A — Disable load for now

Right-click HR_Directory in the Queries pane → uncheck Enable Load. A dialog warns that this will remove the table from the model — click Continue.

The query name will now appear in italics in the Queries pane — this is the visual indicator that a query exists but does not load into the model.

Note for the capstone: If your chosen scenario is HR Workforce Insights (Module 10), you'll revisit this query and implement Option B by creating a SalesRep-to-Employee mapping.
