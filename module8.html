Trend Lines & Forecasting

The Analytics Pane

Select any line or scatter chart → in the Visualizations pane, click the Analytics tab (the magnifying glass icon, next to Format). The Analytics pane exposes reference lines and statistical overlays that are added to the visual without changing the underlying data or model.

Analytics optionWhat it addsBest used for
Trend lineLeast-squares linear trend across all data pointsShowing the overall direction of a time series
ForecastETS (Exponential Triple Smoothing) projection with confidence intervalExtrapolating recent trend forward
Constant lineA horizontal line at a fixed valueTarget / threshold reference
Min / Max lineHorizontal lines at the minimum and maximum values in the seriesShowing range bounds
Average lineHorizontal line at the series meanComparing each period to the overall average
Percentile lineLine at a specified percentileShowing distribution thresholds (e.g. P90)
Forecast Caveats

Power BI's built-in forecast uses ETS, which assumes a seasonal or trend pattern in the existing data. With only 12 monthly data points (2024 only), forecasts have wide confidence intervals and should be labelled clearly as "indicative" rather than predictive. For serious forecasting, use Python/R visuals or Azure ML integration.

Forecasting requires a continuous date axis — it will not work if the X axis contains text (like MonthName). Use Dim_Date[Date] or Dim_Date[Month] on the axis for forecasting.

Decomposition Tree — Practical Notes

The Decomposition Tree is the most useful AI visual for engineering and operations analysts. It answers "why is the total what it is?" by letting users break down a metric by any available dimension — in any order, on the fly. No pre-defined drill path is needed.

The AI split option (lightning bolt icon in the visual) automatically selects the dimension that explains the most variation at each level, using a decision-tree algorithm. You can also split manually by clicking + and choosing the dimension yourself.

What-If Parameters

What They Are

A What-If parameter creates a numeric slicer that lets users pick a value from a range. Power BI automatically:

  1. Creates a single-column calculated table containing the range values
  2. Creates a measure ParameterName Value that returns the currently selected value from the slicer
  3. Adds a slicer for the parameter to the current page

You then write a DAX measure that references the parameter's Value measure to compute a scenario result. The visual updates in real time as the user moves the slicer.

Creating a Parameter

Modeling tab → New parameter → Numeric range. Fill in:

FieldPurpose
NameDisplay name — appears as the table name and the slicer header
Data typeDecimal number or Whole number
Minimum / MaximumRange bounds for the slicer
IncrementStep size between values
Default valueStarting position of the slicer
Usage Pattern
-- After creating "Price Increase %" parameter (0–30, step 5, default 10):

Adjusted Revenue =
[Total Sales] * (1 + 'Price Increase %'[Price Increase % Value] / 100)

-- Moving the slicer from 10 to 20 changes this measure from Total Sales × 1.10
-- to Total Sales × 1.20 instantly, without any model refresh.

Performance Analyzer

What It Measures

View → Performance analyzer → Start recording. Interact with any visual — click a slicer, drill down, hover over a data point. Power BI records the time taken for each visual to refresh, broken into three components:

ComponentWhat it representsHow to improve
DAX query Time the storage engine spent running the measure queries Simplify measures; avoid CALCULATE with FILTER on large tables; use integers for join keys
Visual display Time the visual component spent rendering (drawing, animating) Reduce data points in the visual; disable animations; reduce table row count with Top N
Other Network, JSON serialisation, background tasks Minimal control; affected by Service vs Desktop; network latency
Reading the Results

A DAX query time under 200 ms is excellent. 200–500 ms is acceptable. Over 500 ms for a single visual will be noticeable to users. Over 2000 ms means the report will feel slow and the measure needs investigation.

Click Copy query next to any visual's result to get the DAX query that Power BI sent to the storage engine. Paste it into DAX Studio (free external tool) for detailed profiling with server timings and query plans.

5

Report Optimization

Reduce What the Engine Computes
  • Top N filters on visuals: If a bar chart has 100 products, apply a visual-level Top N filter (Format pane → Filters on this visual → Top N → 10). The query only retrieves 10 rows instead of 100.
  • Disable "Show items with no data": This forces Power BI to compute all combinations including empty cells — usually not needed.
  • Avoid bidirectional relationships: They expand the filter propagation graph and increase query complexity.
  • Use integers for relationship keys: Integer joins are faster than text joins (e.g. use RegionID not RegionName where possible).
Reduce What the Visual Renders
  • Limit scatter chart points: Scatter charts become unreadable and slow above ~3,000 points. Apply a Top N or date filter.
  • Disable cross-report visual interactions where not needed: Every slicer interaction triggers a refresh on every visual it can filter. Use Edit interactions to break unnecessary cross-filter connections.
  • Remove unused visuals and hidden pages: Even invisible visuals consume query resources on page load.
Model-Level Optimizations
  • Remove unused columns in Power Query: Every column in memory is compressed and scanned. Remove columns that are never used in visuals, measures, or relationships before Close & Apply.
  • Set summarization to "Don't summarize" for dimension columns: Right-click a text column → Summarization → Don't summarize. This prevents Power BI from accidentally summing or counting it when dragged into a visual.
  • Avoid calculated columns when a measure will do: Calculated columns multiply memory usage by the row count. A measure computes on demand with no persistent storage.

Storytelling with Data

The SCQA Framework

Effective data stories follow the SCQA structure:

LetterStands forIn a report context
SSituationThe current state shown in KPI cards (e.g. "Total Sales: £315,000")
CComplicationThe problem highlighted (e.g. "3 of 10 regions are below target")
QQuestionWhat the audience needs to know (e.g. "Which products are driving the shortfall?")
AAnswerThe insight the report surfaces (e.g. Decomposition Tree drill into underperforming regions)
Design for the Insight, Not the Data

Most Power BI reports show data. The best reports show insights. The difference: data is "Total Sales by region sorted by name." Insight is "Only 4 of 10 regions hit their Q3 target — highlighting the 6 that missed." Use conditional formatting, reference lines, and annotations to direct the reader's eye to what matters, not just what exists.

Lab 8A — What-If: Price Increase Scenario
1
Create the What-If parameter

On the Modeling tab, click New parameter → Numeric range. Fill in:

  • Name: Price Increase %
  • Data type: Decimal number
  • Minimum: 0
  • Maximum: 30
  • Increment: 5
  • Default value: 10
  • Check Add slicer to this page

Click Create. Power BI creates a table named Price Increase % and a measure named Price Increase % Value. A slider slicer appears on the canvas.

2
Create the Adjusted Revenue measure

Right-click _Measures → New measure: 

Adjusted Revenue =
[Total Sales] * (1 + 'Price Increase %'[Price Increase % Value] / 100)

Format: £#,0.00.

3
Add Adjusted Revenue to the Sales Performance page

Navigate to the Sales Performance page. Add a Card visual for [Adjusted Revenue]. Title it "Revenue at Selected Price Uplift". Move the Price Increase % slicer to this page (cut from the original page → paste here, or re-add it).

Move the slicer to 20% — the Adjusted Revenue card should update to Total Sales × 1.20. Move it back to 10% and confirm it recalculates.

✓ Lab 8A Checkpoint
  • The Price Increase % slider moves between 0% and 30% in steps of 5%.
  • Adjusted Revenue at 0% = Total Sales exactly. At 10% = Total Sales × 1.10. At 30% = Total Sales × 1.30.
  • Adjusted Revenue is sensitive to region and category slicers (it uses [Total Sales] which is filter-context-aware).
Lab 8B — Trend Lines & Anomaly Detection
1
Add a Trend line to the Monthly Sales chart

Go to the Sales Performance page. Select the Monthly Sales and YTD line chart. In the Visualizations pane, click the Analytics tab (magnifying glass icon).

Expand Trend line → toggle On. Set colour to dark orange (#E07030) to distinguish from the monthly sales line. Set line style to dashed.

2
Add an Average line

Still in the Analytics pane, expand Average line → toggle On. Label it "Monthly Avg". Set colour to dark grey. This lets users instantly see which months are above or below average.

3
Add Anomaly Detection

Still in the Analytics pane, expand Find anomalies → toggle On. Power BI will flag any months whose sales value is statistically unusual relative to the trend.

With only 12 monthly data points, the anomaly algorithm has limited statistical power. The feature is more meaningful with daily or weekly data over longer periods. This step demonstrates the capability — whether anomalies are flagged depends on how the generator distributed order dates across months.

Lab 8C — AI Visual: Decomposition Tree
1
Add a new page and create the Decomposition Tree

Add a new report page → name it Sales Analysis. Add a Decomposition Tree visual (in the Visualizations pane, scroll to find the branching tree icon).

Configure the field wells:

  • Analyze: [Total Sales]
  • Explain by: Add all of these in order:
    • Dim_Products[Category]
    • Dim_Products[SubCategory]
    • Dim_Regions[RegionName]
    • Fact_Orders[SalesChannel]
    • Fact_Orders[OrderStatus]
2
Explore the decomposition

The visual starts with the total sales figure. Click the + button next to it and choose Category. The total splits into sales by product category. Click + on the largest category and choose SubCategory to drill further.

Try the AI split (lightning bolt icon): Power BI automatically picks the dimension that explains the most variation at each level — useful for discovery when you don't know where to look.

Click any node to cross-filter the other visuals on the page (if any). Add a Card showing [Total Sales] to confirm cross-filtering works.

Lab 8D — Dynamic Chart Title
1
Create the chart title measure

Right-click _Measures → New measure: 

Chart Title =
"Monthly Sales" &
IF(
    ISFILTERED(Dim_Products[Category]),
    " — " & SELECTEDVALUE(Dim_Products[Category], "Multiple Categories"),
    " — All Categories"
) &
IF(
    ISFILTERED(Dim_Date[QuarterName]),
    ", " & SELECTEDVALUE(Dim_Date[QuarterName], "Multiple Quarters"),
    ", Full Year 2024"
)

This measure returns a text string that reflects the current slicer state. When no slicer is active: "Monthly Sales — All Categories, Full Year 2024". When Electronics is selected: "Monthly Sales — Electronics, Full Year 2024".

2
Apply to the line chart

Go to the Sales Performance page. Select the Monthly Sales line chart. In the Format pane, expand General → Title. Change the Title text field from a fixed string to a measure by clicking the fx button to the right of the Title text box. In the dialog, select Field value → choose [Chart Title] from _Measures. Click OK.

Now select different categories in the Category slicer — the chart title updates automatically.

Lab 8E — Performance Analyzer
1
Run the Performance Analyzer

Go to the Sales Performance page. Click View → Performance analyzer → Start recording. Now interact with the report: select a category in the slicer, select a quarter, click a bar in the regional chart. Stop recording when done.

Expand each visual's result in the Performance analyzer pane. Note the DAX query time, visual display time, and Other time for each.

2
Identify the slowest visual and review its query

The regional detail table (with 6 measures) is likely the slowest visual. Click Copy query next to it. The copied text is the DAX query Power BI sent to the storage engine — you can paste it into DAX Studio or Power BI's new semantic model editor for detailed analysis.

For this dataset (585 orders, 10 regions, 23 measures), all visuals should complete in under 100 ms. Performance analysis becomes critical at 10M+ rows or with dozens of complex measures — this exercise builds the habit.

Lab 8F — Row-Level Security
1
Create an RLS role

On the Modeling tab, click Manage roles → Create. Name the role North England Manager.

In the table list, select Dim_Regions. In the table filter DAX expression box, enter: 

[RegionName] = "North England"

Click Save. This role limits all Dim_Regions data to the single row where RegionName = "North England". All fact table data flows through Dim_Regions via relationships — so Fact_Orders, Fact_Targets, and all measures are automatically limited to North England data only.

2
Test the role

On the Modeling tab, click View as → North England Manager. The report now behaves as if the user is in that role:

  • The Region slicer shows only "North England"
  • The regional bar chart shows only one bar
  • The detail table shows only one region row
  • KPI cards show North England figures only

Click Stop viewing (banner at the top) to return to the full admin view.

3
Dynamic RLS pattern (reference)

In production, roles use USERPRINCIPALNAME() to match the logged-in user's email to a lookup table, so each user's access is determined by a data table rather than a hard-coded DAX rule: 

-- In a RLS table filter on Dim_Regions:
[RegionName] IN
CALCULATETABLE(
    VALUES(UserRegionMap[RegionName]),
    UserRegionMap[UserEmail] = USERPRINCIPALNAME()
)

This requires a UserRegionMap table (uploaded to the model or gateway) mapping email addresses to region names. The setup is done in the Power BI Service after publishing — covered in Module 9.
